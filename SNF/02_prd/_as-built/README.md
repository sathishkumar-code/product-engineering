This entry closes that gap — 58 commits / 17 merges on `pre-production`, 2026-08-10→08-20. **Nothing in this window is in `production`.** A companion system-architect pass covered the same range technically (`docs/architecture/architecture-senior_living_backend.md` v2.6); this entry is the product read of the same delta, plus independent confirmation of several v1.6 admin-side claims against their backend contracts.

- **New Critical gap — G-30 / CLIN-GAP-22: two more `/pcc-sync/*` endpoints gated only by a hardcoded, already-compromised shared secret.** `POST /pcc-sync/syncUpdateResidentBulk` (refreshes demographic fields for every PCC-linked resident) and `POST /pcc-sync/syncResidentCognitoBulk` (idempotent Cognito-account backfill) join a **pre-existing, previously-undocumented** `bulkMedicationSync` endpoint in checking the identical literal `A879B3C-4D5E-6F7G-8H9I-0J1K2L3M4N5O` (`x-sync-secret` header or body `secretKey`) as their only auth gate — a string committed in plaintext to source control across three call sites, so it must be treated as already known to anyone with (current or historical) repo access. Same unauthenticated-outside-`/api` router mount as the fully-open sibling tool already tracked at CLIN-GAP-19 (Critical) — no `facilityMiddleware`, `facilityId` taken from the request body, so a caller with the secret can target any facility. Do not extend this pattern to new endpoints. (clinical-records.md CLIN-FR-22a/CLIN-FR-27, CLIN-GAP-22)
- **Chat retention policy reversed to fully non-destructive — corrects the record, not an extension.** Two commits (2026-07-31, 2026-08-03; code comments cite HIPAA / California's 7-year retention requirement) removed all physical destruction from both chat delete paths: message soft-delete no longer clears content/attachments/reactions or deletes the S3 object (only `deletedAt`/`deletedBy` are set), and destroying a group conversation (creator delete, or automatic last-member-leaves cleanup) no longer hard-deletes messages, the `Conversation` document, the group picture, or any attachment — every read path already gated on `deletedAt` rather than inferring "deleted" from empty fields, so there is no API/socket contract change, only a data-retention behavior change. **messaging-chat.md's prior documentation of "eager S3 deletion at soft-delete time" (MSG-FR-12) and "destroys all group data" (§4.2) was accurate through 2026-07-30 and is now corrected in place**, not merely extended — if any other planning artifact still describes chat delete as destructive, it is stale. A pre-existing bug (predating this change) was fixed as a side effect: a destroyed group's per-member unread count is now cleared, where it previously stayed permanently inflated. (messaging-chat.md §1, MSG-FR-12, §4.2, §6)
- **`ChatSystemUser` — new automated chat-messaging identity; Transportation is the first consumer.** A non-human, per-facility chat identity lets a backend module post automated cards into a facility-configured chat group (`sendModuleMessage()`, reusing the full human-send pipeline — encryption, mentions, receipts, push fan-out). Routing is config-driven per facility (`Config.chat.moduleMessageBindings`, per-event opt-out preference). Transportation posts a full-state card at ride-lifecycle events (create/assign/start/arrive). **No creation API exists** for a `ChatSystemUser` or its bindings — onboarding a facility onto this is a manual database write today, a candidate gap if more modules adopt the pattern before an admin UI exists. New MSG-FR-36, TRN-FR-26. (messaging-chat.md, transportation.md)
- **Resident/family phone-and-email uniqueness enforcement removed at every layer, not just the admin-web UI v1.6 already documented.** v1.6 (admin-only pass) described this as "the client no longer blocks." The backend-side commits show the removal goes deeper: `resident.controller.ts`'s uniqueness check is removed outright (not merely bypassed) from create/update/add-family-member, and the **DB-level unique sparse index** on `FamilyMember({residentId, countryCode, phone})` — the actual data-integrity backstop — was dropped from the schema entirely (2026-08-06). A second, independent advisory-only endpoint was also found: `POST /api/consent-forms/validate-members` (used by the consent-form co-signer picker), unauthenticated like its sibling `check-duplicate`. Net effect: uniqueness is enforced nowhere in this system today — database, backend, or UI — for any caller. New PLAT-FR-73a. (platform-foundation.md)
- **PCC resident onboarding: email-fallback identifier confirmed + a welcome-message asymmetry surfaced.** Confirms and extends v1.6's PCC-onboarding note: `onboardNewResident()`'s Cognito provisioning now independently branches on phone/email existence (email-only account when phone is taken and email is free, and vice versa — previously effectively phone-only-or-nothing). Separately: the welcome SMS/email is now opt-in per call site via a `sendWelcome` flag — `patient.admit` passes it, but `patient.readmit`'s onboarding-when-no-local-resident path (Path B) does not, so a readmit-triggered onboarding provisions a Cognito account silently with no welcome message. Whether this asymmetry is intentional was not confirmed this pass — flagged as a product question. (clinical-records.md CLIN-FR-20d correction)
- **Legacy Cognito user-pool migration: a second, independent path found — this one in password reset, not login.** `forgotPassword`/`resetPassword` for Admin/Staff (`authReset.controller.ts`) now resolve an identifier against a second, legacy Cognito pool (env `OLD_USER_POOL_ID`) when not found in the current one, migrating the account lazily at reset-completion. This is **additive to, not a duplicate of**, the three login-time migrators already tracked (PLAT-FR-72 admin/staff web, PLAT-FR-72a SN resident app, PLAT-FR-72b staff app) — a fourth independently-built codepath toward what is evidently a platform-wide Cognito pool consolidation. Whether all four target the same legacy pool was not confirmed this pass. New PLAT-FR-76. (platform-foundation.md)
- **Confirmed backend contracts for two v1.6 admin-side claims.** (1) The busy-driver "book/approve anyway" confirmation dialog (transportation.md TRN-FR-18c) is backed by a single `respondBookingConfirmation()` helper merging resident-schedule and driver conflicts into one 409 response, exactly as the admin UI assumes. (2) The referral discharge-date backdating window (`Config.dischargeDateMaxPastDays`, default 28, referrals.md REF-FR-10) matches the admin-side client mirror exactly, including the constant name and default value. Both were cited in v1.6 as "confirmed present … but not part of this pass's admin-scoped commit review" — now independently verified. Also confirmed: the KPI Dashboard's "Care & Referral Activity" tile fields (`secureCallsMade`, `referralsSent`, `documentsSigned`) match the backend `DailySummaryReport` additions exactly (dashboard-reporting.md DSH-FR-23) — no correction needed.

## Conventions

- **As-built baseline**: requirements describe current behavior. Half-built, mock, or dead functionality is never stated as a requirement — it appears in module §9 "Observations & candidate gaps" with evidence references.
- **FR numbering**: `<PREFIX>-FR-NN` per module, stable for cross-referencing from the technical evaluation and refactoring plans.
