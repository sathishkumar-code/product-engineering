## 1. Purpose & scope

Transportation lets residents (and family/staff on their behalf) request facility-provided rides to external destinations (doctor visits, shopping, etc.). Each facility defines per-destination-category **transportation rules** that determine whether a ride is complimentary up to a distance limit, plus a facility-level config (price per mile, pickup buffers, max ride distance). Requests flow through an **admin approval workflow** (price set, driver assigned) and a **driver lifecycle** on the staff app (Accept → Start → End). The module integrates Google Places (destination autocomplete) and Google Distance Matrix (road distance / travel time), computes a pickup time from a buffer formula, syncs rides into the cross-module UnifiedSchedule calendar, and emits an event-rich notification stream to resident, family, and transport staff.

In scope: rules CRUD, facility transport config, resident ride request flow (both resident apps), distance/pricing/pickup computation, admin approval + admin-initiated scheduling, driver assignment constraints, driver ride lifecycle (including in-place edit and a dedicated request detail view), statuses, views per persona, notifications/real-time. Out of scope: billing/settlement of ride charges (price is recorded and surfaced in Payment History only), vehicle/fleet management (none exists), route optimization (none exists).

## 3. Functional requirements (as-built)

### Rules & configuration

- **TRN-FR-01 — Transportation rules per destination category.** Each facility maintains `TransportationRule` records, unique per `locationType` (free-text category, e.g. "Doctor visit"): `{ locationType, isComplimentary, complimentaryDistanceLimit (miles, required > 0 when complimentary), isActive }`. (backend §3.1; admin §2.7)
- **TRN-FR-02 — Rules CRUD + toggle (admin web).** `GET /transportation-rules?isActive&isComplimentary` (response also carries `travellingWithOptions[]`), `POST`, `PUT /{id}`, `PATCH /{id}/toggle`, `DELETE /{id}`. List view filters: All / Active / Inactive / Complimentary / Paid. (admin §2.7)
- **TRN-FR-03 — Facility transport config.** `Config.transportation`: `pricePerMiles`, `pickupBufferMin`, `pickupBufferMax`, `pickupBufferMultiplier`, `appointmentDurationOptions[]` (admin default [30, 60, 90, 120] min), optional `MaxMilesForTransport`. Delivered to the admin client in the bootstrap `GET config` payload together with facility `lat`/`lng`. (backend §3.1; admin §1, §2.7)
- **TRN-FR-04 — Active rules drive resident-facing destination choices.** Resident apps populate the destination-type dropdown from `GET /api/transportation-rules?isActive=true`; the admin request form and filters use `GET /resident-transportation/destination-types`. (resident-SL §3.7; resident-SN §3.7; admin §2.7)

### Resident ride request flow

- **TRN-FR-05 — Destination selection via Google Places.** Address chosen through Google Places Autocomplete + Place Details (formatted address + lat/lng). Admin web runs autocomplete client-side and biases by facility coordinates; both resident apps embed Places directly on-device. (admin §2.7; resident-SL §3.7; resident-SN §3.7)
- **TRN-FR-06 — Distance & travel-time calculation.** Road distance and duration from the facility to the destination are computed via **Google Distance Matrix**. Two implementations exist:
  - Server-side: `GET /resident-transportation/calculate-distance?lat&lng[&appointmentStartTime]` (auth) → `{ distance, distanceText, estimatedTravelTime, durationText, pickupTime, maxMiles, facility/destination coords }`; `NoRouteFoundError` → 400. Used by admin web. (backend §3.3; admin §2.7)
  - Client-side: both resident apps call Distance Matrix directly from the device (`src/utils/distanceMatrix.ts`) and submit the resulting distance/time with the booking. (resident-SL §3.7; resident-SN §3.7)
  - **Traffic-aware server estimate (staging + pre-production).** The backend helper `getRoadDistanceFromFacility(origin, destLat, destLng, departureTime = now)` (`lib/transportation.ts`) now requests Distance Matrix with `departure_time` + `traffic_model=best_guess` and returns `duration_in_traffic` when Google provides it (flagged `inTraffic`). Traffic data is used **only for departures at now-or-future**; a past `departureTime` falls back to the traffic-free duration. `ZERO_RESULTS` still raises `NoRouteFoundError`. This tightens the pickup-time estimate (TRN-FR-09) for admin-side scheduling; the on-device resident path is unchanged.
- **TRN-FR-07 — Complimentary-vs-paid determination.** A ride is complimentary when the matched rule has `isComplimentary` **and** `distance ≤ complimentaryDistanceLimit`; price is then 0. Otherwise `price = round(distance × pricePerMiles)` to the cent. `isComplimentary` on the request is **derived server-side, never client input**. Resident apps mirror the check for UX: "complimentary up to X miles" note when within limit; otherwise a mandatory paid-ride agreement checkbox + extra-charge disclaimer. (backend §3.1, §3.3; resident-SL §3.7; resident-SN §3.7)
- **TRN-FR-08 — Max-distance enforcement.** `MaxMilesForTransport` is enforced by the `calculate-distance` precheck with a user-facing message; in admin web a distance beyond `maxMiles` blocks scheduling with a persistent inline error. The booking endpoint itself does **not** re-enforce the cap (see §9-O1). (backend §3.3; admin §2.7)
- **TRN-FR-09 — Pickup-time computation.** Pickup time is derived, never user-entered:
  `pickupTime = appointmentStartTime − (estimatedTravelTime + clamp(estimatedTravelTime × pickupBufferMultiplier, pickupBufferMin, pickupBufferMax))` (`services/transportationRequest.service.ts:96-117`). `pickupTime` is the canonical scheduling anchor on the request; admin shows it read-only; the precheck endpoint can return a suggested pickup time. (backend §3.1, §3.3; admin §2.7)
- **TRN-FR-10 — Booking submission.** `POST /api/resident-transportation/book-transportation` (bookingContext-gated): looks up the active rule for the facility, derives complimentary/price (TRN-FR-07), computes pickupTime (TRN-FR-09), **checks the resident's `UnifiedSchedule` for conflicting appointments**, then creates the request as `Pending` and notifies Transport-permission staff. **Schedule-conflict detection (production 2026-06-23):** before persisting, the booking checks for overlapping entries of types `SALON`, `MASSAGE`, `PT`, `CARE`, `CARE_CONFERENCE`, `REHAB`, `TRANSPORTATION` in the resident's schedule (the `Arrived` status is included in the blocking set). If conflicts are found the endpoint returns **409** with `{ requiresConfirmation: true, conflicts: [...] }` and does **not** create the request. Sending `forceBook: true` in the request body bypasses the conflict check and books regardless. Conflict entries are deduplicated by `(type, from, to)` to prevent repeated rows from multiple UnifiedSchedule entries for the same slot. Request fields: destinationType + `destinationRuleId`, address, `appointmentStartTime` (UTC instant), `estimatedTravelTime` (min), optional `appointmentDuration`, `distance` (miles), `travellingWith ∈ alone | with_family | with_caregiver`, `roundTrip`, special request, `createdByType/CName`, optional `forceBook`. (backend §3.1, §3.3)
- **TRN-FR-11 — Resident form composition & validation (apps).**
  - SL app: destination type, address (Places), appointment date-time bounded **tomorrow … +2 months**, duration dropdown (10/15/30/45/60 min), optional special request, travelling-with (options from API), Round Trip checkbox; inline validation for destination, geocoded address, future date-time, duration, travelling-with, and the paid-ride agreement when chargeable. **As of staging the SL app books via `POST /api/resident-transportation/book-transportation`** (`createResidentTransportation`, `src/services/Home/index.tsx:284`) — the legacy `POST /api/resident-transportation` path is gone, so the SL and SN apps now use the same server-deriving booking endpoint (O8 resolved). Both success and failure route to a confirmation screen. (resident-SL `TransportationScreen` + `services/Home`)
  - SN app: same conceptual flow (rules-driven destination type, Places autocomplete, client Distance Matrix, complimentary determination), books via `POST /api/resident-transportation/book-transportation`. **As of `origin/master` HEAD `4734daf` (2026-08-21):** the booking response's server-computed `pickupTime` and `distance` are now displayed back to the resident (previously collected but not shown); a `409` conflict response (TRN-FR-10) now opens a `SchedulingConflictModal` listing the conflicting appointments, with a "Book Anyway" action that resubmits with `forceBook: true` — this is the resident-app-side consumer of a conflict contract the backend has offered since production 2026-06-23 but this app previously didn't surface. (resident-SN §3.7; `TransportationScreen/index.tsx`, `SchedulingConflictModal`)
- **TRN-FR-12 — On-behalf booking policy.** Booking and resident views are gated by `resolveBookingContext`: residents always self-service (any supplied `residentCName` ignored — spoof guard); family members allowed per facility config; staff must supply a resident identifier and have a designation in `bookingPermission.TransportationRequest.staffDesignationAllowed` (or an allowed designation group); admin/super-admin bypass the designation check. A parallel `/case-manager/resident/:residentId/...` route family lets any STAFF act by resident `_id`, bypassing `resolveBookingContext` (role check only). (backend §0.3, §3.4)

### Resident views

- **TRN-FR-13 — My requests & history.** `GET /my-requests` (Pending/Approved/Started, future or in-progress), `GET /my-requests/history`, and `GET /my-requests/list` (flexible filters: pickupDate, status list, upcoming) — all bookingContext-gated. **As of staging the SL app also has Upcoming/History segments** (`TransportationListScreen/index.tsx` — `upcomingRides`/`historyRides` via `fetchResidentTransportationHistory`), matching the SN app; status badges (Approved green / Pending yellow / Canceled red / other gray), address, formatted date-time, duration, travelling-with. Still **no resident-facing cancel or edit actions** on either app (§9-O12). (backend §3.4; resident-SL `TransportationListScreen`; resident-SN §3.7)
- **TRN-FR-13a — Ride detail screen, resident-facing (NEW, `senior_living_skillednursing_resident`, `origin/master` HEAD `4734daf`).** A dedicated read-only `TransportationDetailsScreen` lets a resident open a single ride from their Upcoming/History list (TRN-FR-13) to see its full detail (destination, pickup time, price, round-trip flag, special request, travelling-with, driver info where assigned) — the resident-facing counterpart of the staff app's driver-facing detail screen (TRN-FR-20a). Presentation-layer only; no new backend endpoint, and does not add a cancel/edit action (§9-O12 still open). (`src/screens/App/Transportation/TransportationDetailsScreen/index.tsx`)
- **TRN-FR-14 — Calendar integration.** Every request syncs a `TRANSPORTATION` row into UnifiedSchedule (Mongoose post-save/update/delete hooks) and appears in the SN app's My Schedule unified agenda and detail bottom-sheet. TRANSPORTATION rows are written to the calendar but deliberately **excluded** from the cross-venue booking-conflict blocking set (a ride does not block a salon/massage/PT/care/rehab slot). (backend §0.4; resident-SN §3.5)

### Admin approval workflow

- **TRN-FR-15 — Request queue.** `GET /resident-transportation?search&status&destinationType&page&limit`; filters: text search (resident/destination/address), status, destination type, driver (driver filter param stubbed — §9-O2). Legacy `GET /` scoping: ADMIN sees all; STAFF-only sees requests assigned to them. (admin §2.7; backend §3.4)
- **TRN-FR-16 — Approve with price + driver ("Set Ride Price" modal).** Clicking a Pending row opens the approval modal: price* (USD ≥ 0; 0 = complimentary; manual entry — auto-calculation from `pricePerMiles` is not implemented in the UI, §9-O5), pickup time read-only, driver dropdown (staff by designation; **skipped when the approver's role is STAFF**). Accept = `POST /resident-transportation/{id}/assign { cName }` + `PUT /resident-transportation/{id} { status: "Approved", price, priceRemarks }`; Reject = status `Rejected`. Completed/Rejected rows open read-only detail. (admin §2.7)
- **TRN-FR-17 — Driver assignment constraints (backend).** `POST /:requestId/assign` (ADMIN/STAFF): allowed only from `Pending` or `Approved`; staff may only **self-assign** (cannot take another driver's request); admin may assign any active staff by cName; **driver-overlap rule** — the driver must not already hold another `Approved` request whose `[pickupTime, appointmentStartTime + estimatedTravelTime]` window overlaps (`transportationRequest.controller.ts:1376-1408`). Successful assign sets status `Approved`. (backend §3.2)
- **TRN-FR-17a — Outside-agency driver assignment (production 2026-06-22).** `TransportationRequest` now supports an **outside-agency driver** — a driver not in the facility's Staff collection. Two mutually exclusive driver modes:
  - **Facility staff driver** (`cName` field as before) — subject to the TRN-FR-17 overlap check and self-assign rules.
  - **Outside-agency driver** — an `agencyDriverName` string (free text, captured in the admin approval modal) with no StaffcName required. When an outside-agency driver is used, the standard staff-overlap check is skipped (no Staff record to query). `TransportationRule` records can now carry `outsideAgency` configuration.
  The admin approval modal (`AppointmentsTransport.tsx`) now includes a **driver name input field** for cases where a driver from an external agency is assigned (production 2026-06-28).

- **TRN-FR-17b — Case-manager visibility across all residents (production 2026-06-22).** A new route family (`GET /case-manager/residents/:residentId/transportation-requests` and related) lets staff with the Case Manager designation view transport requests for **all residents assigned to them** — bypassing the standard per-resident `resolveBookingContext` and keying instead on the caller's designation. A `designationDispatch.middleware.ts` routes requests to the appropriate handler based on the caller's staff designation. The existing `PATCH /:id/manage` path is unchanged; the case-manager route is additive.

- **TRN-FR-18 — Combined manage update.** `PATCH /:id/manage` (ADMIN/STAFF): driver + status + price + priceRemarks in one call. A staff user assigning someone **other than themselves** must have a designation in `bookingPermission.TransportationRequest.staffDesignationAllowed` (`canStaffManageTransportationAssignments`). Driver assignment implies `Approved` unless an explicit status accompanies it. Status and price are applied **as-is — no transition matrix** (§9-O6). `Arrived` is settable via this route. (backend §3.2)

- **TRN-FR-18a — Driver-change detection on edit (staging + pre-production).** `manageTransportationRequest` now snapshots the prior driver (`previousDriverCName` / `previousIsOutsideAgency` / `previousDriverName`) and recomputes a `driverChanged` flag via a `normalizeCName` helper, so re-submitting the **same** driver on an unrelated edit (e.g. a notes-only change) **no longer re-fires the "driver assigned" notification**. Only a genuine driver change re-notifies. (`transportationRequest.controller.ts`)

- **TRN-FR-18b — Admin-panel edit access & inline designation resolution (staging + pre-production).** The manage/list surface gained an `isAdminPanel` query flag (`transportationListQuerySchema`), and the route-level `dispatchByStaffDesignation` middleware was **replaced by inline resolution** in the controller: `isTransportDriverStaff()` checks the staff `designation` **and its resolved parent designation** (`resolveParentDesignation` against `Config.staffDirectoryRoles`) to decide transport-driver access, rather than a separate dispatch middleware; the prior "calendar view is admin-only" 403 guard was likewise removed inline. The admin web complements this with **edit permissions gated by user role + request status** (a request past certain statuses / owned by another role is not editable). *(This shifts the designation gate from middleware into the controller — see §9-O15 on the commented-out `dispatchByStaffDesignation`.)*

- **TRN-FR-18c — Busy-driver confirmation ("book/approve anyway") (pre-production, NEW, v1.6).** The driver-overlap rule (TRN-FR-17, BR-5) previously hard-blocked assignment; a driver-overlap now instead returns a **confirmable** conflict, surfaced identically on the two admin driver-assignment paths:
  - **Approval ("Set Ride Price" modal, `AppointmentsTransport.tsx`):** accepting a Pending request with an overlapping driver returns `{driverConflict: true, driverConflictMessage}` instead of a hard error; a **"Driver Is Busy"** confirmation dialog offers "Approve Anyway" (resubmits with `forceDriverAssign: true`) or "Cancel".
  - **Schedule/Edit Transport modal (`useScheduleTransportModal.tsx`):** the same `driverConflict` response is merged into the **existing** resident-schedule-conflict dialog (TRN-FR-10's 409 `{requiresConfirmation, conflicts}`) so only **one** confirmation dialog is ever shown even when both a resident-schedule overlap and a driver overlap occur together — a single "book anyway?" click resends the payload with `forceBook` and/or `forceDriverAssign` as applicable, accumulating overrides across retries in case a second guard trips after the first is confirmed.
  This makes the driver-overlap rule (BR-5) an **overridable warning, not a hard constraint**, for admin/staff with edit access — mirroring the resident-schedule-conflict pattern already established by TRN-FR-10. (`senior_living_admin` `AppointmentsTransport.tsx`, `useScheduleTransportModal.tsx`, `errorMiddleware.ts`; `senior_living_backend` `transportationRequest.controller.ts`)
- **TRN-FR-19 — Admin-initiated scheduling on behalf of residents.** "Schedule Transport" (canEdit-gated): resident combobox, destination type (from rules), address autocomplete, appointment date/time, duration (from `appointmentDurationOptions`), special request, travelling-with, round trip, price*, auto pickup time, driver* → `POST /resident-transportation/book-transportation` then immediately approve + assign. (admin §2.7)
  The admin `TransportCalendar` component now applies **timezone-aware formatting** for event date and time (production 2026-06-29) and shows **resident availability information** (from `UnifiedSchedule`) in appointment detail popovers (production 2026-06-29). The `AppointmentsTransport` table now displays an expandable notes column for special requests (production 2026-06-29). Driver conflict detection also runs at the schedule-transport path for admin users (production 2026-06-28).

- **TRN-FR-19a — New-admission ("prospect") rides (staging + pre-production).** The schedule flow can now book a ride for a **person who is not yet a resident** — a new admission arriving at the facility — without a `Resident` record or a destination rule. `TransportationRequest` gained `isNewAdmission`, `newAdmissionName`, `newAdmissionPhone`, `newAdmissionNotes` (with `destinationType`/rule made **conditionally not-required** when `isNewAdmission`), plus a `resident` **virtual** that synthesizes a pseudo-resident (`{name: newAdmissionName, …}`) so downstream views and notifications render uniformly. New-admission bookings **skip the transportation-rule / complimentary-pricing lookup entirely** and persist only a recomputed distance. Duration is derived as `newAdmissionDuration = appointmentDuration ?? Config.newAdmissionDefaultTravelMinutes ?? 30 min`. On edit, `newAdmissionName` / `newAdmissionPhone` are writable **only when** the request is a new-admission (`manageTransportationBodySchema`). The admin web surfaces this as a new-admission mode in the Schedule Transport form (name/phone/notes inputs, optional appointment-duration selection, pickup-time preserved from user input rather than overwritten). (`TransportationRequest.model.ts`, `transportation.schema.ts`, `transportationRequest.controller.ts`; admin `AppointmentsTransport`)

- **TRN-FR-19b — Admin update confirmation & discard-changes dialogs (pre-production).** Editing an existing transport/appointment request in the admin web now opens a **confirmation dialog before committing an update** ("Update Ride" / "Are you sure you want to update this transportation request?") and a **discard-changes confirmation** ("Keep Editing" / "Discard") when the user navigates away from an edited-but-unsaved schedule form (gated on a live dirty-check against an `initialScheduleSnapshot`, so a clean close is silent) — closing the prior silent-overwrite / silent-loss behaviour on the admin schedule-edit path. Presentation-layer only; no backend contract change. (admin `AppointmentsTransport.tsx`, merged to `pre-production`)

- **TRN-FR-19c — Calendar edit/delete + reusable schedule modal + soft-delete (pre-production, v1.5).** The Schedule/Edit Transport modal was **extracted into a reusable hook** `useScheduleTransportModal` so it can be opened from **both** the request list and the calendar. `TransportCalendar` now lets edit-capable users **edit or delete a ride directly from the calendar** detail popup (disabled for past-date rides), with delete going through a confirmation dialog and a new **soft-delete** mutation (`DELETE /resident-transportation/:id` → status `Deleted`; `use-transport-requests.ts`). The calendar plots only `Approved`/`Pending` (completed/rejected filtered client-side), shows a "Booking Date" (= `createdAt`) in the popup, and UI statuses gained `Arrived`/`Cancelled`/`Deleted`. Query note: `statusIn` is now sent **comma-separated** (Express-5 query-parser fix), not as an array. **Terminology:** an admin-wide **"Transportation" → "Transport"** label sweep renamed the sidebar nav item + subitems ("Transport", "Transport Rules") and headings across `ComplimentaryTransport.tsx`/`AccessManagement.tsx`/`DesignationManagement.tsx`. (admin `useScheduleTransportModal.tsx`, `TransportCalendar.tsx`, `use-transport-requests.ts`)

Each event template shares one builder/renderer (`transportationChatTemplates.ts`) and owns its own `resolveMentions`. ## 5. Notifications & real-time behavior

- **Event-rich push stream** (`services/transportRequest.notification.service.ts`, 1,291 ln — FCM, logged to `NotificationHistory`): request created (→ Transport-permission staff), driver assignment (→ driver + resident + previous driver on reassignment), driver arrived, ride started, ride completed, ride cancelled/rejected, and a "request updated" on status/price/detail changes. Resident, family, and transport staff each receive tailored bodies. (backend §3.5)
- **"Ride Updated" now also reaches the assigned driver (staging + pre-production).** `notifyTransportRequestUpdated()` was extended to push the update to the **assigned driver** in addition to resident/staff (title `TRANSPORTATION_REQUEST_UPDATED_DRIVER_TITLE = "Ride Updated"`; body `"Your assigned ride has been updated. Tap to view the latest ride details"`; FCM `type: TRANSPORTATION_REQUEST_UPDATED`). The re-notify is gated by `driverChanged` for the driver-assignment case (TRN-FR-18a) so a no-op re-save is silent.
- **Update bodies deliberately kept generic (iteration reverted).** A "detailed change reporting" iteration that appended a before/after `changeSummary` / `extraChanges` diff to the resident/staff update bodies was **added and then removed** ("simplify transportation request update notifications by removing detailed change reporting"). Final as-built state (staging **and** pre-production): update notifications are generic — `"Your/A transportation request for {destinationType} has been updated."` with no change diff.
- **Ride reminders**: per-facility configurable offsets via the notification cron (default every minute; env default lead 15 min) scanning UnifiedSchedule; TRANSPORTATION maps to module `TRANSPORT`, event `RIDE_REMINDER`. Duplicate-send protection via unique `NotificationSentLog (scheduleId, offsetMinutes)`. Staff reminders route by Transport page permission. (backend §0.5)
- **Real-time (staff app)**: Transport Driver subscribes to socket events `mobile-TransportationRequest-request-upserted` / `-deleted`; updates render as a visible "refresh" mode with scroll-to-top. Socket auth carries Bearer token + `x-facility-id`. (staff §5)
- **Calendar real-time**: UnifiedSchedule sync emits `emitUnifiedScheduleUpserted` / `emitUnifiedScheduleDeleted` socket events consumed by schedule surfaces. (backend §0.4)
- Admin web approval toast asserts "…Caregiver has been automatically notified" after accept. (admin §2.7)

## 8. Product-split notes

- **Shared backend, per-repo app split.** Both resident apps (Senior Living `com.shashigroup.sal.resident` and Skilled Nursing `com.shashigroup.sl.resident`) hit the same backend and the same transportation endpoints; the product split is per-repo/per-app, not a runtime flag. Transportation behaves identically in concept on both; this module applies to **Both** products. (resident-SN header)
- **Feature parity deltas between the two resident apps**: as of staging the gap has narrowed sharply — both apps now have Upcoming/History segments (TRN-FR-13), **both book via `book-transportation`** (the SL legacy-path divergence is gone — §9-O8), and the SL app derives facility coordinates from the facility-config API rather than a hardcoded India fallback (§9-O3). The SN app's unified-schedule agenda integration remains the residual delta.
- **No facilityType conditionals** were found in the transportation code paths of admin web (the SNF/AL split there is data-driven by facility-enabled pages); the Transport nav item appears wherever the facility-pages API enables it. (admin §3)
- **Staff app is product-agnostic**: the Transport Driver view keys purely off the staff designation, not facility type. The staging edit-in-place flow and request detail screen (TRN-FR-20a/20b) are likewise facility-type-agnostic. (staff §1)
- **The new case-manager Transport tab (TRN-FR-25) is SN-flavored in practice, unlike the driver view.** It is role-gated to Case Manager/Social Worker/Director of Nursing — designations that exist predominantly on the Skilled Nursing tab bar (MIGRATED app flow) — so, unlike the facility-type-agnostic driver queue, this surface is reachable only by staff already routed into the Skilled Nursing experience (personas-and-roles.md §2.2).
- For a unified product, transportation is one of the cleanest "already shared" modules — convergence work is app-level (endpoint choice, history segment, status-label spelling) rather than backend-level.

## 9. Observations & candidate gaps

> Engineering/product follow-ups surfaced by code analysis. Each has an evidence ref; none are documented product decisions.

- **O1 — Client-trusted distance, travel time, and (apps) pricing inputs.** The booking endpoint trusts client-provided `distance` and `estimatedTravelTime`; `MaxMilesForTransport` is enforced only in the `calculate-distance` precheck, and resident apps compute distance on-device — so a modified client could submit an under-reported distance to obtain a complimentary/cheaper or over-limit ride. `isComplimentary` is server-derived, but from the client-supplied distance. *Evidence:* backend §3.3 note; backend §8 item 5. *Candidate fix:* recompute distance server-side at booking from address lat/lng and re-enforce the cap.
- **O2 — Stubbed driver filter in admin queue.** The driver filter param is commented out pending backend support — `// TODO: Uncomment when backend is implemented` (`use-transport-requests.ts:80,221`, the admin repo's only TODOs). *Impact:* dispatchers cannot filter the queue by driver.
- **O3 — Hardcoded Google API keys (India restriction RESOLVED on staging).** The SL app's Vadodara fallback coords and `components: 'country:in'` restriction are gone — autocomplete now biases to facility coords from the facility-config API with a US (NYC) fallback (`TransportationScreen/index.tsx:443,484-485`). The **hardcoded Places key remains** (`local.constants.ts`), as does the SN app's hardcoded key (`local.constants.ts:6`). *Candidate fix (still open):* move keys to build config / proxy through backend.
- **O4 — Unauthenticated endpoints.** Transportation-rule CRUD routes carry no auth (`transportationRule.routes.ts`); `GET /resident-transportation/:id` and `GET /destination-types` are unauthenticated. Anyone with the base URL (+ facility id header) could mutate rules or read a ride (address, resident linkage). *Evidence:* backend §3.1, §3.4, §8 item 1.
- **O5 — Price auto-calculation not implemented in admin UI.** `pricePerMiles` is delivered to the admin client but the "Set Ride Price" modal requires manual entry; the server-computed booking price and the admin-entered approval price can diverge with no reconciliation. *Evidence:* admin §2.7.
- **O6 — No transition matrix on manage/PUT.** `PATCH /:id/manage` and `PUT /{id}` apply status and price as-is — e.g. Completed → Pending or price changes after completion are possible. Enforcement exists only on assign/start/end. *Evidence:* backend §3.2.
- **O7 — Commented-out schema validation on rules.** The complimentary/limit invariant validation in `transportationRule.model.ts:48-66` is commented out; only the booking controller re-validates — direct rule writes (incl. via the unauthenticated routes, O4) can persist invalid rules. *Evidence:* backend §3.1, §8 item 9.
- **O8 — RESOLVED on staging: single booking endpoint.** The SL app now posts to `POST /api/resident-transportation/book-transportation` like the SN app and admin (server derives complimentary/price/pickup); the legacy `POST /api/resident-transportation` self-`Pending` path is no longer used. The endpoint-divergence parity/abuse risk is closed. *Evidence:* `services/Home/index.tsx:284` (`createResidentTransportation`).
- **O9 — Status-label inconsistencies.** SL app renders `'Canceled'` (one L) while sibling modules use `'CANCELLED'`; admin's type union includes `Started` with no UI; staff app shows `Rejected` with no action. *Evidence:* resident-SL §6 ("Canceled one L"); admin §2.7; staff §4.1.
- **O10 — Admin max-miles error can silently de-sync.** The over-limit inline error clears only on address re-selection; changing the appointment time can silently re-invalidate the computed values. *Evidence:* admin §2.7 / §4.4.
- **O11 — Driver card under-displays data (partially addressed on staging).** `TransportRequestData` carries round trip, complimentary flag, price, special request, travellingWith, distance, duration, resident & driver objects; the compact driver-queue card still does not surface most of these, but the new dedicated request detail screen (TRN-FR-20a) gives drivers a place to see the full record before acting. *Evidence:* staff §4.1, staff §270 item 4; staff-app review 2026-07-12.
- **O12 — No resident cancel/edit.** Neither resident app offers cancel or edit on a submitted request, despite `Cancelled` being a backend status and a cancellation notification existing — cancellations are admin/staff-only today. The new staff-app edit-in-place flow (TRN-FR-20b) is staff/driver-facing only and does not change this for residents. *Evidence:* resident-SL §3.7 ("No cancel/edit actions"); backend §3.2, §3.5.
- **O13 — Round trip has no scheduling semantics.** `roundTrip` is a stored boolean with no return-leg scheduling, second pickup time, or doubled pricing logic anywhere in the analyzed flows. *Evidence:* backend §3.1 (field only); admin/staff/resident sections (display/input only).
- **O14 — Notification toggles not persisted (SL).** The SL app's transport notification toggle is local-only state. *Evidence:* resident-SL §2 NotificationsSettingScreen.
- **O15 — Designation gate moved from middleware into the controller (staging).** The route-level `dispatchByStaffDesignation` middleware and the calendar-view "admin only" 403 guard were **commented out** and replaced by inline checks (`isTransportDriverStaff` / `resolveParentDesignation`) inside `manageTransportationRequest` (TRN-FR-18b). This works but relocates an authorization decision from a declarative middleware into controller branching, where it is easier to miss on a future edit; the commented-out middleware should be removed or the inline logic re-extracted. *Evidence:* `transportationRequest.controller.ts` (commits `3577f81d`, `964c61ed`).
- **O16 — New-admission rides inherit the client-trusted-distance gap (O1) with no rule backstop.** New-admission bookings (TRN-FR-19a) skip the rule/pricing lookup and persist only a recomputed distance, so the O1 concern (client-supplied distance, cap enforced only in the precheck) applies here with even less server-side validation — there is no destination rule to bound the ride. *Evidence:* `transportationRequest.controller.ts` new-admission branch.
- **O17 — New Transport tab vs. legacy case-manager Transport screens: relationship unresolved (2026-08-21, NEW).** The new Skilled Nursing `TransportScreen` tab (TRN-FR-25) and the pre-existing `TransportationRequestScreen`/`TransportationListScreen` case-manager surfaces both appear reachable by the same Case Manager/Social Worker/Director of Nursing designations. Whether this is a deliberate list-detail split (tab = live overview, existing screens = create/edit detail) or an unintentional duplicate build was **not disambiguated this pass** — a product decision, not an engineering guess. *Evidence:* `architecture-senior_living_staffapp.md` §3.2b, §10 item 1; `skilledNursingAppStack/index.tsx`.
