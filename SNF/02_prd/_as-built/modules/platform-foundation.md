## 1. Purpose & scope

Platform Foundation is the substrate every other module stands on: multi-tenancy, identity & authentication, personas, staff designations, the access-permission model, resident lifecycle (platform view), family-member linkage, and app version management.

In scope:

- **Multi-tenancy** — the `x-facility-id` header model, the per-facility `Config` document (the de-facto facility record), `accessPages` feature switching, `bookingPermission` on-behalf booking policy, and the `IntegrationAvailable` / PMS integration registry.
- **Identity & authentication** — AWS Cognito with phone-number-first usernames, MFA (SMS-preferred; TOTP on web/SL clients), forced password change, forgot password, credential provisioning ("Send Credentials", now with Cognito-invite suppression + a custom welcome message — PLAT-FR-14c), inactivity logout, and token refresh. Also covers the facility-configurable, device-level biometric App Lock now built independently on the staff app (PLAT-FR-75) and the SN resident app (PLAT-FR-77).
- **Personas** — SUPER_ADMIN, ADMIN, STAFF, RESIDENT, FAMILY_MEMBER, plus the TV device identity (which impersonates a resident).
- **Staff designations & designation groups** — the facility-configurable role catalogue and the hardcoded care-team / rehab / supervision / directory-hidden sets.
- **Access-permission model** — per-page read/write grants, designation permission templates, parent/child sync rules, and the two-filter visibility model.
- **Resident lifecycle** — admission/CRUD, careType, statuses, room/unit assignment, SNF care-team role assignments, payment history.
- **Family-member linkage** — max-count limit, family auth normalized to resident identity, `hasPortalAccess`.
- **App version management** — per-bundle force-update minimums, plus the SN resident app's Expo/EAS JS-bundle OTA update pipeline (PLAT-FR-78).

Out of scope (covered by sibling module docs): notifications platform internals, TV pairing/content, chat, all domain modules (dining, wellness, transport, clinical, etc.).

## 3. Functional requirements (as-built)

### 3.A Multi-tenancy & facility model

**PLAT-FR-01 — Tenant scoping via `x-facility-id` header.**
Every `/api/*` request (except `/api/config` discovery, `/api/app-version`, the pre-facility `/api/auth/*` OTP-reset router, and `/api/fax/*` which mounts before the global gate — `app.ts:99-104`) passes through facility middleware that reads the `x-facility-id` (or legacy `facilityid`) header and scopes Mongo queries by facility. Clients inject the header automatically: the admin web stores `facilityId` from the login profile; the staff app persists a selected/auto-bound `FACILITY_ID`; the SN resident app derives it from `GET /api/config/residency-details` on first Home focus. Socket connections carry the facility in handshake headers/auth.
*Business rule (as-built defect):* the missing-header guard compares against `null`/`''` but the value is `undefined` when absent, so the 400 never fires and an omitted header yields an **empty facility filter — cross-tenant reads are possible** (`facilityMiddleware.ts:41`, `src/lib/facility.ts:51-54`). See §9. *(Note: a new, unrelated instance of this same gap class — a manual PCC-sync tool that reads `facilityId` from an unauthenticated request body — shipped 2026-07-10; documented in clinical-records.md CLIN-GAP-19 rather than duplicated here, since it is scoped to that module's routes.)*

**PLAT-FR-02 — Facility = one `Config` document; no Facility collection.**
The per-facility `Config` document keyed by `facilityId` *is* the facility record. It bundles: identity/branding (concierge number, lat/lng, timezone default `America/Los_Angeles`, theme colors, logo, acknowledgement PDF, **optional `facilityLicenseNumber` string** added production 2026-06-24 — used in referral PDF generation), feature visibility (`accessPages`), the staff designation catalogue, permission templates (`defaultPermissions`), booking policy (`bookingPermission`), dining/transport/rehab/chat module settings, PMS wiring (`pms[]`, `integratedModules`), and security/UX knobs (`inactivityTimeout.{web,mobile}`, `maxFutureBookingDays`, `maxFamilyMembersCount`).
*Business rules:* there is no facility lifecycle API — Config documents are created out-of-band; several read/written fields (`designations`, `facilityName`, `tvSetupLocations`, `familyRelations`) are absent from the schema and persisted only via `strict:false` writes.

**PLAT-FR-03 — Per-facility feature switching via `accessPages`.**
`Config.accessPages[]` (`{name, isHidden, rank, children[]}`) is the facility's navigation/feature switchboard (defaults list 15 top-level pages). Hidden pages are stripped for **everyone, including ADMIN** — this is the mechanism that produces the Senior Living vs Skilled Nursing product variants (e.g., which Rehab sub-page set a facility sees). Staff then see only the remaining pages matching their read permissions. `rank` drives nav ordering on the admin web; page-name matching is normalized (lowercase, strip non-alphanumerics) on both grant storage and checks.

**PLAT-FR-04 — On-behalf booking policy (`bookingPermission`).**
Per-module policy (keys: SalonAppointment, MassageAppointment, PrivateTrainingAppointment, TransportationRequest, FamilyMealRequest, Care, RehabAppointment, Housekeeping) resolved by booking-context middleware:
1. RESIDENT — always allowed self-service; any supplied `residentCName` is ignored (spoof guard).
2. FAMILY_MEMBER — allowed iff `isFamilyMemberAllowed`; can book only for the linked resident.
3. STAFF — must supply a resident identifier; allowed iff their designation is in `staffDesignationAllowed` (with designation-group expansion).
4. ADMIN/SUPER_ADMIN — bypass the designation check, but the module policy must exist (per-facility opt-in).
Missing policy = deny for everyone except residents. Result is a normalized `bookingContext` (`createdByType`, `createdByCName`, `residentCName`) consumed by booking modules.

**PLAT-FR-05 — Integration registry (`IntegrationAvailable` + `Config.pms[]`).**
Two tenant-scoped registries wire external systems: `Config.pms[]` declares providers (`OPERA | POINTCLICKCARE | YARDI | TELS | CUSTOM`) with an `integratedModules` map (module → provider; validated to reference only configured providers), and `IntegrationAvailable` holds per-facility PCC org/facility credentials (externalId, orgUuid, clientId/clientSecret, token, isActive). PCC webhook handlers map inbound PCC `facId`/`orgUuid` back to a facility through this collection. Presence of a PCC row effectively turns on SNF-style clinical sync (patients, medications, discharge webhooks — including, as of 2026-07-10, fully automated resident onboarding on admission; see clinical-records.md CLIN-FR-20d).
*As-built risk:* client secrets stored in plaintext in Mongo (§9).

**PLAT-FR-06 — Facility discovery.**
`GET /api/config/getAllfacility` (optional auth) powers app login/facility-pick screens: STAFF callers receive only their own facility; everyone else — including unauthenticated callers — receives all facilities (id, concierge number, coordinates, designations, facilityName, tvSetupLocations, familyRelations). `GET /api/config/get-facility-data` returns the same projection for one facility and opportunistically upserts the caller's FCM token. The staff app auto-binds single-facility staff to the first facility (no picker shown); switching facilities requires logout.
*As-built gap:* `GET /api/config/` returns the entire raw facility config with **no auth** (§9).

**PLAT-FR-07 — Product split is emergent, not a flag.**
There is no facility-level `productType` field in the backend. "Senior Living vs Skilled Nursing" is assembled from four mechanisms: resident-level `careType`, the rehab therapy-type fork (fixed AL therapy types vs SNF `therapyType: 'OTHER'` + dynamic `RehabTherapy` catalogue), `accessPages` visibility, and integration presence (PCC/TELS/Lemedix). The **admin web** additionally holds a two-value client-side `facilityType` enum (`SKILLED_NURSING | ASSISTED_LIVING`, returned by `GET config`) used for table layouts, labels ("Room No" vs "Unit No"), care-type locking, and document headers. See §8.

### 3.B Identity & authentication

**PLAT-FR-10 — Phone-first Cognito identity.**
All human personas authenticate against an AWS Cognito user pool; the **Cognito username is the E.164 phone number** and doubles as the platform person key (`cName`). Roles come from the `cognito:groups` claim of the access token (groups: SUPER_ADMIN, ADMIN, STAFF, RESIDENT, FAMILY_MEMBER). Clients use `USER_PASSWORD_AUTH` (admin web computes a SECRET_HASH client-side). Email is optional, **non-unique**, and normalized everywhere: on `Admin`, `Staff`, and `Resident` the `email` field is `required:false` with a **sparse, non-unique** index (the same address may be shared across people/facilities); all create/update paths preprocess email to `trim().toLowerCase()`, empty/whitespace/`null` collapse to "no email", and an invalid address is dropped to `undefined` rather than rejecting the request (`Admin.model.ts:26-27`, `Staff.model.ts:187`, `resident.model.ts:107`; validators `resident.schema.ts:9-20`, `admin.schema.ts:10-20`, `staff.schema.ts:50-64`). Phone uniqueness: global per Admin/Staff collections; per-facility for residents; per-resident for family members. A person can hold multiple personas only via the same phone resolving to one Cognito user (`createOrResolveCognitoUserByPhone`).
*Client divergence:* the SL resident app signs in with an **email-form** login field, while the SN resident app, staff app, and admin web are phone-first — a UX inconsistency over the same phone-username pool.

**PLAT-FR-11 — Token verification & session model.**
Bearer access tokens are verified via JWKS against the pool issuer (`token_use === 'access'`). Clients persist access/id/refresh tokens (localStorage on web, AsyncStorage/Keychain on mobile), silently refresh near expiry (single-flight refresh queues), and support "Remember Me" credential storage in the device keychain on mobile. Logout on web revokes the refresh token and clears state; on mobile it calls `POST /api/{staff|residents}/logout` (which clears the stored FCM push token server-side) then signs out of Cognito.
*Admin-web refresh resilience (as-built):* token refresh now clears the session **only** for definitive Cognito auth errors (`NotAuthorizedException`, `UserNotFoundException`, `UserNotConfirmedException`, `InvalidParameterException`, `ExpiredTokenException`); transient/network failures keep the session alive for retry (e.g. after laptop sleep). Refresh is single-flight via a promise queue; the app bootstrap retries refresh up to 3 times with linear back-off (0/1/2 s); `clearTokens()` removes only auth keys and facility state, preserving user settings/permissions/active-view (`tokenService.ts:16-31,35-36,163-169`; `MainApp.tsx:145-161`). **"Remember me"** selects token persistence: when checked, tokens are written to `localStorage` (survive restart) and the phone is saved under `rememberedPhone` for pre-fill; when unchecked, tokens live in `sessionStorage` only and any `localStorage` copies are purged (`tokenService.ts:50-65`; `LoginPage.tsx:124-136`). The **SECRET_HASH** for refresh is computed from the Cognito **username (E.164 phone)** via `COGNITO_USERNAME` (falling back to `cName` then email), not the email attribute which can diverge after rehydration (`tokenService.ts:107-127`).
*As-built quirks:* web token-refresh buffer is still 1 minute where the comment says 5 (admin `tokenService.ts:87-89`); the SL resident app has **no logout UI at all** (§9).

**PLAT-FR-12 — Challenge flows: forced password change and MFA.**
Login responses are routed by challenge: `NEW_PASSWORD_REQUIRED` (admin-provisioned accounts) → forced password change (policy: ≥8 chars, upper, lower, digit, special), which may chain into MFA challenges; `MFA_SETUP` → TOTP enrollment (QR + manual secret on web; manual-key-only on the staff app); `SOFTWARE_TOKEN_MFA` / `SMS_MFA` → 6-digit code verification (SMS auto-read on Android — the staff and SN resident apps use `react-native-otp-verify` and a custom-OTP SMS-consent library for this autofill; confirmed still accurate against production as of the 2026-07-12 skilled-nursing resident-app review, no change needed here); `MFA_SELECT` → factor-choice prompt (staff app).
*Server policy:* provisioning **forces SMS MFA as preferred** for every created user unless env `MFA_ENFORCE=false`; the server-side helper explicitly disables TOTP — yet web and SL-app clients implement full TOTP enrollment flows (drift; §9). MFA reset is exposed as `POST /api/residents/resetMFA` (clears MFA settings + best-effort global sign-out) and is callable from the unauthenticated admin login screen ("Lost Device?").
*Admin-web MFA surface (as-built):* a dedicated 6-digit MFA verification screen handles both `SMS_MFA` ("code sent to {email}") and `SOFTWARE_TOKEN_MFA` ("code from your authenticator app") with boxed digit inputs, paste support, auto-advance/backspace, Enter-to-submit, and a 30 s resend countdown; on success it calls `RespondToAuthChallenge` and stores tokens. The same component embeds a **"Lost Device" MFA-reset sub-flow** (`init-reset → verification-code → setup-mfa`) running Cognito `ForgotPassword`/`ConfirmForgotPassword` (email-keyed) so a user who lost their authenticator can reset their password and re-enroll (`MFAVerification.tsx:51-199,255-267`). This client retains full TOTP UI despite the server forcing SMS-preferred / disabling TOTP — the §9 item 14 drift stands.

**PLAT-FR-13 — Forgot password (Cognito-native).**
Cognito-native reset: request a code (delivered to the phone), then confirm with code + new password under the same password policy. The admin web's `ForgotPassword.tsx` drives this path directly (`ForgotPasswordCommand` / `ConfirmForgotPasswordCommand`).

**PLAT-FR-72 — Email-or-phone login, MFA-channel selection & user-pool migration (pre-production, NEW).** The admin/staff login was reworked so a person with either a phone or an email (or both) can sign in on the channel they prefer:
- **Identifier toggle.** `LoginPage.tsx` shows a phone/email segmented control; `resolveUsername()` normalizes the entry, and email is validated with `EMAIL_REGEX`. This makes staff/admin **email login** a first-class path (previously phone-first only), consistent with the now-optional-phone staff/resident accounts (PLAT-FR-10).
- **MFA-channel pinning.** Before `InitiateAuth`, the client calls a new **`POST /api/auth/login-mfa-channel { identifier, channel }`** (rate-limited 120 / 15 min per NAT IP; `authMfaChannel.controller.ts` → `selectLoginMfaChannel`, mounted pre-facility) so a dual-contact account receives the OTP on the channel the user chose rather than a server default.
- **`EMAIL_OTP` / `SELECT_MFA_TYPE` challenges.** The client handles Cognito `SELECT_MFA_TYPE` (auto-selecting SMS for phone, EMAIL_OTP for email — no picker) and the **`EMAIL_OTP`** challenge (code "emailed to …", "didn't receive email" resend), threaded through `AuthFlow.tsx`/`MFAVerification.tsx`/`PasswordChange.tsx`. Forgot-password and send-credentials now accept `{ phone? | email? }` (`StaffForgotPassword.tsx`, hooks `use-forgot-password-staff`/`use-verify-otp-staff`/`use-reset-password-staff`/`use-send-credentials`).
- **Legacy user-pool migration.** On an `InitiateAuth` failure, `userPoolMigrator.ts` calls a **migrator Lambda** (`VITE_USERPOOL_MIGRATOR_URL`, falling back to a hardcoded pre-prod API-Gateway URL) with `{username, password}`, then retries sign-in once — transparently migrating accounts from an older Cognito pool.
- **"Remember me" semantics changed** — now only pre-fills the identifier (method + phone/email under `rememberedLoginMethod`/`rememberedEmail`); tokens are **always** persistent, so it no longer shortens the session (contrast the earlier persistence-toggle behavior in PLAT-FR-11).
- **Orphan:** a **passwordless resident-login** screen (`ResidentLogin.tsx`, Cognito `USER_AUTH` choice flow offering `EMAIL_OTP`/`SMS_OTP` first factor) was built but is **imported nowhere** — unreachable in this build; a candidate to wire up or remove (§9).
- ⚠ **Build-config drift:** the admin app now reads the REST/socket base URLs from `VITE_PREPROD_URL` / `VITE_SOCKET_PREPROD_URL` (this doc and CLAUDE.md document `VITE_PROD_URL` / `VITE_SOCKET_PROD_URL`) — a pre-production-branch artifact to reconcile before a production build. (`api.ts`, `socket.ts`, `chatSocket.ts`)

**PLAT-FR-72a — Passwordless sign-in, SN resident app only (NEW, `senior_living_skillednursing_resident`, `origin/master` HEAD `4734daf`).** Independent of, and architecturally distinct from, PLAT-FR-72: the SN resident app's entire sign-in surface was rewritten from phone+password to a Cognito `USER_AUTH` (`EMAIL_OTP` / `SMS_OTP` first-factor) challenge flow, driven **directly against Cognito** by the mobile client via `@aws-sdk/client-cognito-identity-provider` (`initiateUserAuth()` / `respondToOtpChallenge()`, `cognitoUserAuth.service.ts`) — the backend is not in the login request path at all (contrast PLAT-FR-72's `POST /api/auth/login-mfa-channel`, which stays backend-mediated). `SignInScreen` collects a phone-or-email identifier; a `preferredChallengeFor()` heuristic picks `SMS_OTP` for a phone-shaped value and `EMAIL_OTP` for an email-shaped one; `MFAVerifyScreen` (repurposed from the old MFA-verify screen) now takes `{ username, session, contact, challengeType }` and resolves via `RespondToAuthChallengeCommand`. `ChangePasswordScreen`, `ForgotPasswordScreen`, `ResetPasswordScreen`, and the Profile `ChangeUserPassword` screen (plus their tests) were **deleted** — there is no password-based fallback and no in-app password-change surface. The custom-OTP backend reset flow (PLAT-FR-13a: `/api/auth/forgot-password`, `/api/auth/reset-password`) and the temp-password probe (`check-temp-password`, second `PLAT-FR-14a`) are **no longer called from this app** (still live for other clients — see those FRs).
*Dual Cognito SDK stack (as-built debt, not a defect):* the app now runs **two** Cognito client libraries side by side — the new `@aws-sdk/client-cognito-identity-provider` path owns sign-in; the legacy `amazon-cognito-identity-js` path (`cognito.service.ts`) is retained, reduced to `refreshSession()`/`logout()` only. This is intentional per the repo's own engineering notes (do not merge the two stacks without a scoped ticket) but is a real maintenance surface — two SDKs, two config resolution paths (`cognito.config.ts` carries both a sync `COGNITO_CONFIG` and an async `getActiveCognitoConfig()`), and a Hermes-polyfill dependency (buffer, web-streams, text-encoding, `structuredClone`/`Blob.arrayBuffer` shims in `index.js`) the new SDK requires to boot at all on React Native's JS engine.
*Product framing:* this closes the "orphaned passwordless resident-login screen" gap noted in PLAT-FR-72 (`ResidentLogin.tsx`, admin repo, unwired) — but as a **separate, independently-built implementation** in the resident app, not that orphaned screen being wired up. **PLAT-FR-13a — Custom OTP password reset (phone-based, resident/family).**
Independent of the Cognito-native reset, the backend exposes a self-built 3-call OTP flow mounted at `/api/auth/*` **before** the facility middleware, so it needs no `x-facility-id` header and no auth token (`app.ts:99`):
- `POST /api/auth/forgot-password { phone }` — validates E.164, looks up the Cognito user by phone; if the user is not `CONFIRMED` (still on a temporary password) it returns **403** ("use your temporary password / contact your administrator"); otherwise it generates a 6-digit OTP, SHA-256-hashes it, stores one `PasswordResetOtp` row per phone, and sends the OTP by SMS. Responses are deliberately generic ("If the account exists, an OTP has been sent.") to avoid account enumeration.
- `POST /api/auth/verify-otp { phone, otp }` — validates the OTP without consuming it (gates the UI's "next" step).
- `POST /api/auth/reset-password { phone, otp, newPassword }` — re-validates the OTP, sets a permanent Cognito password (`AdminSetUserPassword Permanent:true`), revokes all sessions (`AdminUserGlobalSignOut`), and single-uses the OTP (deletes all rows for the phone).

**OTP policy:** TTL 300 s (`OTP_TTL_SECONDS`; SMS copy says "Valid for 5 minutes"); max 3 verify/reset attempts per OTP (`OTP_MAX_ATTEMPTS`), after which the OTP is deleted and a 429 returned; per-phone resend cooldown 60 s (`OTP_RESEND_COOLDOWN_SECONDS`, silently absorbed); rows auto-expire via a Mongo TTL index on `expiresAt`; password min length 8 at the API boundary, Cognito `InvalidPasswordException` mapped to 400. Route-level rate limits: forgot 5/15 min, verify+reset 10/15 min. The admin web's `StaffForgotPassword.tsx` (phone → 6-digit OTP → new password) consumes this path, now as **three distinct UI steps** via `use-forgot-password-staff.ts` → `use-verify-otp-staff.ts` (`POST /auth/verify-otp`) → `use-reset-password-staff.ts`. The SN and staff mobile apps also consume the same `/api/auth/{forgot,reset}-password` flow for custom-OTP reset. (`authReset.routes.ts:8-24`; `authReset.controller.ts:23-161`; `PasswordResetOtp.model.ts:13-27`; `cognitoReset.service.ts:30-45`)

**PLAT-FR-21 — Family-member identity normalization.**
When an authenticated caller's groups include `FAMILY_MEMBER`, auth middleware looks up the FamilyMember by Cognito username, resolves the linked Resident, and **rewrites `req.user.username` to the resident's cName**, setting `isFamilyMember`, `residentId`, `familyMemberId`, `familyMemberCName`. Downstream modules can therefore always treat the request identity as "the resident in scope". The same normalization applies to chat socket auth. This is the platform's core family-portal mechanism — even though neither resident mobile app currently ships a family login mode (family members are managed as data; `hasPortalAccess` + the normalization imply the portal capability exists server-side).

**PLAT-FR-22 — TV device identity (summary; full flow in the TV module doc).**
TVs register openly per facility, display a QR pairing session (120 s TTL), and a **resident in the same room** (resident.unitNo must equal the session's unitNo) authorizes pairing from the mobile app. The TV exchanges the authorized session for an access JWT (30 min) + refresh token (30 days, hashed at rest, single active session per user-device). Every TV request additionally requires a live server-side `TvAuthToken` record, so revocation works inside the JWT window. The TV operates with the resident's identity and (socket-path-only) Cognito groups.
*As-built inconsistency:* the HTTP exchange path does not persist `groups` on the token, so HTTP-paired TVs run with empty groups while socket-paired TVs carry the resident's groups (§9).

**PLAT-FR-33 — Per-facility staff-directory role visibility (`Config.staffDirectoryRoles`).**

### 3.E Access-permission model

**PLAT-FR-40 — Permission shape & semantics.**
`Staff.accessPermissions` is a strictly 2-level tree mirroring `Config.accessPages`: `[{name, allowed, isRead, isWrite, children[]}]`. Access levels: NONE (false/false), READ (true/false), WRITE (true/true); `isWrite` implies `isRead`. Legacy records with only `allowed: true` default to READ. Readability/writability **propagate upward** (a readable child makes the parent readable). `syncPermissions` rebuilds a staff member's grants to match the current accessPages structure (drops unknown names, preserves matching grants).

**PLAT-FR-41 — Three-layer designation templates at staff creation.**
On staff create, `accessPermissions` is computed by merging, in ascending priority: `defaultPermissions.global` → `defaultPermissions.designationGroup[<group of designation>]` → `defaultPermissions.designations[<exact designation>]`. Per-staff overrides applied later in Access Management win over templates.

**PLAT-FR-42 — Two-filter visibility model (admin web).**
Page visibility = Filter 1 ∩ Filter 2:
- *Filter 1 — facility-enabled pages* (`GET config/access-pages/all`): applies to everyone including ADMIN; no admin bypass. This is the product-variant switch.
- *Filter 2 — staff permissions*: ADMIN bypasses; STAFF visibility from their permission tree. Sub-item inheritance: a child with its own entry uses it; a child with no entry inherits the parent **unless** a sibling is explicitly granted (then "unlisted = not granted").
Per-page gating in components uses `usePageAccess(pageKey)` → `{canView, canEdit, isReadOnly}`; the universal write-gate pattern is disabled controls + a "You have read-only access" toast — read-only users see pages rather than losing them.

**PLAT-FR-43 — Parent/child sync rules in the Access Management editor.**
When editing a staff member's grants: setting `isWrite` forces `isRead`; checking a parent applies to all children; checking a child derives parent state (parent read = any child read; parent write = any child write); unchecking a parent unchecks children; unchecking the last child unchecks the parent. Saves go to `PATCH /staff/{id}/access-permissions` and invalidate the staff profile so a logged-in staff member's nav updates on next fetch.

**PLAT-FR-44 — Server-side enforcement.**
Permission middlewares (`requireAll/AnyStaffPermission[s]`, write variants) enforce per-page grants **only when the caller is STAFF**; ADMIN/RESIDENT pass through (expected to be gated by role middleware). Canonical permission names: Dashboard, Salon, Housekeeping, Dining, Access Management, Residents, Services, Transport, Maintenance, Massage Therapy, Rehab, Settings. Staff profile responses filter out permissions whose page is hidden in `accessPages`.
*As-built gaps:* the permission-edit route itself lacks auth middleware; the staff mobile app declares but **never reads** `accessPermissions` — its gating is purely designation-based (§9). The new Pending Sign navigation decision (PLAT-FR-30a) is likewise designation-based, not permission-tree-based.

### 3.F Resident lifecycle (platform view)

**PLAT-FR-50 — Admission (create resident + family in one transaction).**
`POST /api/residents` runs a Mongo transaction: create the resident's Cognito user (phone-first, SMS MFA, RESIDENT group) — **only if `isAuthorizedAppAccess` is true** (PLAT-FR-14b) — → insert the `Resident` document (name, birthDate, gender, required `unitNo` and `careType`, **required `admissionDate`** (validated, format-checked — production 2026-07-02), status default `Active`, optional PCC linkage fields; **emergency contact fields removed** from the model, schema, and controller in production 2026-06-21) → for each family member, create-or-resolve a Cognito user (idempotent by phone), add to FAMILY_MEMBER group, insert linked `FamilyMember` rows → commit. On any error the transaction aborts and all newly created Cognito users are best-effort deleted. If PCC fields are present, a fire-and-forget medication sync pulls PCC medications and KMS-envelope-encrypts every field before upserting.
Admin-web form: two steps — demographics (care type auto-set from facilityType and locked) then role assignments + family members. PCC patient rows can prefill the form. **This manual path remains the admission mechanism for facilities without a PCC integration; PCC-integrated facilities now have a fully automated alternative that bypasses this manual step entirely — see clinical-records.md CLIN-FR-20d (rewritten 2026-07-10).**
*As-built gap:* this route carries **no auth middleware** (§9).

**PLAT-FR-51 — Care type.**
`careType` is required on every resident: `assisted_living | memory_care | independent_living | skilled_nursing`. List endpoints filter by `?careType=`; the admin web locks the filter to `skilled_nursing` for SNF facilities and locks the field in create/edit forms. A facility "is" SNF only insofar as its residents are (no facility flag — PLAT-FR-07).
*Related, staging (2026-07-02 → 2026-07-07):* `resident.phone`/`countryCode` are now **optional** on the schema (previously required), and the resident document gained `isSynced`/`pccSyncStatus` fields tracking PCC linkage state — shared by both the automated onboarding webhook flow (clinical-records.md CLIN-FR-20d) and the new manual PCC-sync tool (CLIN-FR-22/CLIN-GAP-19). A resident can therefore now exist with no phone number and, consequently, no Cognito account (PLAT-FR-50's Cognito-creation step is skipped entirely, not merely gated by `isAuthorizedAppAccess`) until a phone becomes available via admin edit, PCC `updateResidentInfo`, or the manual sync tool. (`resident.model.ts` +12 lines; `resident.schema.ts` +5; `residentPhone.validation.ts` +37, tolerant of legacy blank/malformed stored phones; `resident.controller.ts` +291/-…, deferred Cognito provisioning; `senior_living_backend` production HEAD `e075f578`)

**PLAT-FR-52 — Statuses & state machine.**
Schema enum: `Active | Away | Discharged | Transferred` (the TS type omits `Transferred`; the admin UI's filter/badges additionally use `Inactive` — three-way drift). Transitions are manual via Edit (Active/Away/Discharged offered) or driven by PCC webhooks (discharge/transfer/cancel) for PCC-linked facilities. `dischargeDate` is recorded. Soft delete via `deletedAt`; listings filter deleted rows.
*As-built gap:* "Discharged" is settable but not filterable in the admin list — discharged residents cannot be located by status (§9).

**PLAT-FR-53 — Room/unit assignment.**
`unitNo` (required string) is the resident's room; labeled "Room No" (SNF) vs "Unit No" (AL) in the admin UI. PCC-sourced rows display `roomDesc-bedDesc`. `unitNo` is also the authorization join key for TV pairing (resident may only authorize a TV in their own room).

**PLAT-FR-54 — Care-team assignment via unified `assignedStaff[]` (staging refactor).**
The five legacy flat care-team fields (`nurse, caseManager, socialWorker, doctor, dietitian`) were **removed** and replaced by a single indexed `Resident.assignedStaff: string[]` array of Staff cNames, with an `assignedStaffDocs` populate virtual for full profiles (`resident.model.ts:33,94,153`). Any designation may appear in the array — the designation→field 1:1 mapping no longer exists. The admin Add/Edit form still offers role-labelled staff dropdowns but persists every selection into the one array (edited via the shared `StaffMultiSelect` control). The SNF residents table surfaces assigned staff from `assignedStaff`. Chat and notification scoping (PLAT-FR-21, CARE-FR-63, Messaging §4.1) now key on **membership in `assignedStaff[]`** rather than on a specific designation field. A one-time migration script (`src/scripts/migrateAssignedStaff.ts`) consolidates the old fields into the array.
*As-built risk (build item — `SL-TD-14`):* the migration is a **manual** script, not wired into boot or CI/CD — a missed run leaves `assignedStaff` empty and silently empties all care-team chat/notification scoping.
*Per-designation assignment requirements (production 2026-06-21):* a `requireAnyStaffDesignation` middleware function was added (`roleMiddleware.ts`) to enforce that certain routes (e.g., advance care directives) are only callable by staff who have a designated role. A companion `designations.ts` constants update adds a `REQUIRED_STAFF_DESIGNATIONS` set. Per-resident assignment requirements enforce that designated role slots (Case Manager, Social Worker, Doctor) are populated at appropriate workflow points.

**PLAT-FR-55 — Resident edit & identity immutability.**
`PUT /residents/{id}` (multipart). The resident's own phone is **read-only after creation** (it is the Cognito username) **when a phone exists** — a resident admitted without one (PLAT-FR-51) can have a phone added later via this route, which now also carries the deferred Cognito-provisioning trigger (CLIN-FR-20d's `updateResidentInfo` companion applies to the PCC path specifically; the manual admin edit path provisions the same way as initial admission). The emergency contact field itself was removed platform-wide (PLAT-FR-50). Care type is locked. Detail fetch backfills fields not present in the list payload.

**PLAT-FR-56 — Profile, attestation, preferences.**
`GET /api/residents/profile` (self) updates `profileFetchAt` (the "has ever logged in" marker driving Send Credentials visibility) and upserts the FCM token. Residents have a pictures gallery, profile picture upload, directory favorites (`favoritedBy`) and contact-sharing (`shareContact`). An acknowledgement workflow lets the facility upload a PDF (`Config.acknowledgementPdf`) which residents and staff attest to (`acknowledgement: true` + timestamp). Per-user notification preferences cover keys DINING, SALON, TRANSPORT, HOUSE_KEEPING, REHAB (missing key = ON).

**PLAT-FR-57 — Payment history.**
`GET /residents/{id}/payment-history?month=` aggregates a resident's billable activity for a month: summary (totalAmount, totalActivitiesCount) plus line items typed `TRANSPORT | SALON | MASSAGE | PT | MEAL | WELLNESS`, each with a detail view (status, date/time, location, provider, amount). Surfaced as a per-resident modal in the admin web (ungated dollar-icon action).

**PLAT-FR-58 — Deletion semantics by persona.**
Resident: soft delete (`deletedAt`) + best-effort Cognito delete; family-member Cognito users are **not cascaded**. Staff: soft delete (`active:false`) in a transaction + best-effort Cognito delete; **within the same transaction the deleted staff member's `cName` is `$pull`ed from every non-deleted resident's `assignedStaff[]` array** (bulk `updateMany` over `{ deletedAt: null, assignedStaff: cName }`), so a removed staffer no longer dangles on resident records — replacing the prior per-field `$unset` over the five legacy care-team fields (`staff.controller.ts:747-749`). Admin: hard delete of both Mongo doc and Cognito user.

**PLAT-FR-59 — Resident re-admission (reactivate, do not duplicate).**
Re-admitting a previously discharged/deleted resident SHALL **reactivate the existing soft-deleted record**, not create a second one. When a resident is re-added whose prior record is soft-deleted — matched on `{facilityId, countryCode, phone}` (equivalently `cName`) — the system shall **clear `deletedAt`**, set `status` back to `Active` (or the value supplied), and re-create/re-enable the phone-based Cognito user, so exactly **one** row exists per phone and the prior `status`, care-team mappings, family members, and PCC linkage are retained. The same rule applies to the PCC `patient.readmit` path (PLAT/CLIN convergent state): clearing `deletedAt` is part of converging a readmitted resident to `Active`.
*As-built gap (build item — `SL-TD-07`):* the current create path instead **inserts a new document** (fresh `_id`, same `cName = phone`) and leaves the old soft-deleted row in place — and the PCC `readmit` handler sets `status: Active` without clearing `deletedAt` (CLIN-GAP-18). Because `cName = phone` is not uniquely indexed and ~15 identity lookups omit `deletedAt: null`, the resulting live+dead pair can resolve to the dead row (`SL-TD-09`). Reactivation collapses this to a single row. (`resident.controller.ts` create `:408-434`, delete `:1804-1845`; PCC `handlers/patient/readmit.ts`.)

### 3.G Family-member linkage

**PLAT-FR-60 — Linkage model.**
`FamilyMember.residentId` links each family member to exactly one resident (1→N). Fields: name, relation (admin web offers Spouse/Son/Daughter/Brother/Sister; the SN resident app sources options from `facilityData.familyRelations` and removes already-used single-instance relations), `type: Emergency | Family`, `countryCode` (default `+1`), `phone` (now optional, default `''`), email, `hasPortalAccess` (drives Cognito provisioning on update flows), plus PCC contact-sync fields `pcc_contactId` (indexed) and `pcc_is_guarantor`. Per-resident phone uniqueness is enforced by a **unique-sparse** compound index `{residentId, countryCode, phone}` (`familyMember.model.ts:36-62`). These fields are written both by the manual admin/resident flows and by the PCC `patient.updateContactInfo` / `patient.admit` contact-sync handlers (Clinical Records §3D).

**PLAT-FR-61 — Max-count limit.**
`Config.maxFamilyMembersCount` caps family members per resident, enforced at add time (admin web toasts when exceeded; the SN resident app hardcodes a max of 4 in its Manage Account screen — client constant vs config value, a consistency risk).

**PLAT-FR-62 — Post-admission family management.**
Add (`POST /api/residents/add-family-member`, auth): resident must exist and not be deleted; Cognito user created or resolved by phone; **a phone already linked to a family member of a different resident is rejected** (with Cognito rollback if newly created). Edit (`PUT /edit-family-member`); remove (`POST /remove-family-member`) performs Cognito global sign-out → disable → delete. The resident performs the same operations self-service in the SN app.

**PLAT-FR-63 — Family auth = resident scope.**
See PLAT-FR-21: a logged-in family member is normalized to the linked resident's identity for all downstream reads/writes, gated per module by `bookingPermission.isFamilyMemberAllowed` (PLAT-FR-04).

### 3.H App version management

**PLAT-FR-70 — Per-bundle version floor.**
`AppVersion` documents (`bundleId` unique) carry `androidVersion`/`iosVersion` (latest) and `androidForceUpdateVersion`/`iosForceUpdateVersion` (minimum allowed). Single public read `GET /api/app-version/:bundleId`, mounted before the facility middleware so no tenant header is needed — mobile apps check it pre-login to drive force-update prompts. **No write API exists**; rows are managed directly in the database.

**PLAT-FR-78 — Expo/EAS JS-bundle OTA updates, SN resident app (NEW, `senior_living_skillednursing_resident`, `origin/master` HEAD `f22dc60`).** Distinct from PLAT-FR-70's native force-update gate (which blocks on an app-store binary version floor): this app was migrated onto the Expo/EAS Update runtime (`app.json`: `updates.enabled: true`, `checkAutomatically: "NEVER"`, `runtimeVersion: "1.0.0"`; `eas.json` channels `staging`/`preprod`/`production`) so a JS-only bundle can be pushed to installed apps **without an app-store review cycle**. `useOtaUpdate()` (mounted app-wide in `RootNavigator`) checks on mount and on every foreground transition; a positive `expo-updates` check is additionally gated server-side via a new **`GET /api/ota/check`** eligibility call (facility/JWT-scoped — `cName`/facility are inferred server-side, not sent by the client) before anything downloads, and a **`POST /api/ota/log`** delivery-audit call fires once the update is fetched. The update is downloaded in the background but **never applied silently** — an explicit Reload/Cancel dialog is shown, plus a persistent reminder banner (`GlobalOtaBanner`, rendered on SignIn and Home) that stays up across a Cancel and re-opens the same dialog on tap; only tapping Reload calls `Updates.reloadAsync()`. A one-time "update applied" toast (`useOtaUpdateToast`) fires on the next boot, keyed by the specific update id so it never repeats. Because native builds in this repo go through Gradle/Fastlane directly rather than `eas build`, a new build-time script (`scripts/configure-ota-channel.js`, `OTA_CHANNEL=staging|preprod|production`) must be run to patch the channel into `AndroidManifest.xml` and `ios/SkilledNursing/Supporting/Expo.plist` before each native build — nothing does this automatically. **Product framing:** this is the same category of capability already flagged for the staff app (personas-and-roles.md: "now also OTA-updatable via Expo/EAS — not a product requirement"), but the resident-app implementation is more product-visible and more deliberately gated — a server-side eligibility check per facility/platform, plus explicit user-facing reload consent — rather than an invisible background mechanism. No rollback runbook or admin-facing OTA-version management surface was found in this client repo; if one exists it is backend-only and out of this pass's scope. (`app.json`, `eas.json`, `scripts/configure-ota-channel.js`, `src/hooks/useOtaUpdate.ts`, `src/hooks/useOtaUpdateToast.ts`, `src/store/features/otaBanner/*`, `src/components/GlobalAlert/GlobalOtaBanner.tsx`, `src/services/App/index.ts` (`fetchOtaEligibility`, `logOtaDelivery`), `src/services/App/type.ts`)

### 3.I Session & activity tracking

**PLAT-FR-71 — User activity tracking (residents & staff) — staging + pre-production.**
A new platform-wide, append-only activity log records session and device events for both residents and staff. Clients POST to `POST /profile/activity` — exposed on **both** the resident and staff routers (`recordProfileActivity` → `recordUserActivity`, `services/userActivity.service.ts`), body validated by `userActivity.schema.ts` (discriminated on `eventType`).
- **Event model (`userActivity.model.ts`, new):** one document per event — `userType` (`STAFF | RESIDENT | FAMILY`), `cName` (subject; the resident's cName for RESIDENT/FAMILY), optional `actorCName` (the family member's own cName when a family member acts as the resident), optional `facilityId`; `eventType` (`USER_INFO | LOGIN | LOGOUT`); `occurredAt` (client-reported, server fallback); optional `logoutType` (`USER_INITIATED | AUTO_INACTIVITY` — captures the HIPAA inactivity auto-logout, prd-skilled-nursing §6); device fields `deviceOS` / `deviceOSVersion` / `appVersion` / `notificationSubscribed`; optional `fcmToken`. A **TTL index auto-prunes events after `USER_ACTIVITY_TTL_DAYS = 180`**; indexed on `{userType, cName, occurredAt}` and `{facilityId, occurredAt}`.
- **Denormalized "latest activity" snapshot:** each event also overwrites a small set of latest-state fields on the owning document — `lastLoginAt`, `lastLogoutAt`, `lastLogoutType`, `deviceOS`, `deviceOSVersion`, `appVersion`, `notificationSubscribed` — on `Staff` (for STAFF) or `Resident` (for RESIDENT/FAMILY), so an admin can see a resident's/staff member's last-seen + device without scanning the log.
- **Product intent:** this is the substrate for "who is actually using the apps" reporting and for auto-inactivity-logout auditing; there is **no admin-web surface for it yet** (backend-ahead-of-UI). The admin chat cross-window sync already emits a client-side `USER_ACTIVITY` BroadcastChannel message (messaging-chat.md MSG-FR-28), separate from this backend log.

## 5. Notifications & real-time behavior

Foundation-level only (the notifications platform has its own module doc):

- **Push-token lifecycle**: FCM tokens are upserted opportunistically from the `x-fcm-token` header on profile/config fetches; "logout" endpoints clear the stored push token. The staff app registers the FCM token at Splash before any auth routing.
- **In-app identity rooms**: the `/notifications` socket namespace is Cognito-authenticated and rooms users by `user:<cName>` — persona identity (and family→resident normalization) is what notification addressing keys on.
- **Provisioning SMS**: temporary passwords and credential resends are delivered via SMS — as of 2026-07-02, via the invite-suppression + custom-welcome-message path (PLAT-FR-14c) rather than Cognito's default `DesiredDeliveryMediums: ['SMS']` invite copy.
- **OTP/SMS sender ID**: OTP SMS (PLAT-FR-13a/13b) is sent via AWS SNS as a `Transactional` message. For non-US numbers (phone not starting `+1`), if `SNS_SENDER_ID` is configured the message attaches the DLT-registered `AWS.SNS.SMS.SenderID`; US numbers and unconfigured deployments send without a sender ID (a code comment flags SNS→India as a Msg91/Twilio swap point). (`sms.service.ts:6-22`)
- **Real-time tenancy caveat**: unified-schedule socket events on the default namespace are emitted globally (`io.emit`) with no facility scoping and no auth — a foundation-level isolation gap (§9).

## 7. Permissions & access control

Layered model, evaluated in this order:

1. **Authentication** — Cognito access token (or TV JWT + live server-side token record). Family members normalized to resident identity.
2. **Role gates** — `requireAnyRole` / `requireAllRoles` / `requireRoleWithAdmin` against Cognito groups.
3. **Facility feature gate** — `Config.accessPages.isHidden` removes a module per facility for all roles.
4. **Staff page permissions** — read/write tree (PLAT-FR-40–44); enforced server-side for STAFF only; ADMIN bypass.
5. **Booking-context policy** — per-module on-behalf rules (PLAT-FR-04).

Known enforcement asymmetries (full list in §9): a substantial set of mutating backend routes carry no auth middleware at all (resident CRUD, staff toggle/permissions/delete, most config writes); the staff mobile app ignores `accessPermissions` entirely (designation-only gating); four admin-web modules (IDT Report, Care Conferences, Referrals, Messages) have no frontend permission gate and rely on nav filtering + backend. **New (2026-07-10):** a manual PCC-sync ops tool (`/pcc-sync/*`) mounted outside the `/api` prefix carries no auth at all and reads `facilityId` from an unauthenticated request body — documented in clinical-records.md CLIN-GAP-19 as it is scoped to that module's routes, but it is the same enforcement-asymmetry pattern described here.

## 8. Product-split notes (Senior Living vs Skilled Nursing)

- **No backend product flag.** The split is emergent: resident `careType` + `accessPages` visibility + the rehab therapy-type fork (`therapyType: 'OTHER'` ⇒ SNF) + integration presence (PCC ⇒ SNF clinical cluster). PRD recommendation from the analysis: introduce an explicit facility-level product flag if the SKUs diverge further.
- **Client-side facility type.** The admin web recognizes exactly two values (`SKILLED_NURSING | ASSISTED_LIVING`) from `GET config` — used for residents-table layout (SNF shows Case Manager/Social Worker/Doctor columns), room labels, care-type locking, AL therapy vocabulary, and document headers. Memory Care and Independent Living exist only as resident care types, not facility variants — a 4-value resident taxonomy under a 2-value facility enum.
- **Persona/auth divergence between resident apps — widened, not narrowed, by the SN passwordless rewrite (PLAT-FR-72a).** SN app: **passwordless OTP** (`EMAIL_OTP`/`SMS_OTP`) sign-in driven directly against Cognito, no password screens at all, family management, TV pairing, residency-revocation handling (PLAT-FR-16), mid-session family-revocation handling (PLAT-FR-16a, new), sign-out, self-delete. SL app: email-form **password** login, full TOTP setup flows, family members as display data only, no logout UI, profile screens largely hardcoded. Foundation behavior should be identical; today the two resident apps use different Cognito auth flows entirely (password+MFA vs. passwordless-OTP), not just different login-field conventions.
- **Designation sets skew SNF.** The `supervision` group (13 leadership roles) and required care-team assignments (Case Manager/Social Worker/Doctor/Dietitian) encode an SNF org chart; AL deployments rely on the free-form per-facility designation catalogue. **The new designation-driven Pending Sign navigation (PLAT-FR-30a) reinforces this skew** — it is reachable only by staff whose designation resolves to Doctor, a role that is functionally SNF-flavored under the current model even though the designation catalogue itself is facility-configurable and not formally gated by facility type.
- **Foundation is otherwise shared.** Tenancy, Cognito identity, permission model, booking-context policy, family normalization, TV identity, and app-version management are identical infrastructure for both products. The 2026-07 additions (welcome-SMS suppression, the facility-timezone client layer, the automated PCC-onboarding path) are likewise platform-wide mechanisms, even though PCC onboarding in practice only fires for PCC-integrated (predominantly SNF) facilities.
- **Device-level biometric App Lock is now independently built on both a resident client and the staff client** (PLAT-FR-77 / PLAT-FR-75) — same device-scoped enrollment design on both, not a shared library. Neither the SL resident app nor the admin web has an equivalent gate.

## 9. Observations & candidate gaps

Technical-evaluation seeds, each with evidence ref (file paths cited from the analyses).

**Security — tenancy & auth (highest priority):**

1. **Facility header effectively optional → cross-tenant reads.** The missing-header guard checks `null`/`''` but value is `undefined`; `getFacilityFilter` then returns `{}` (`facilityMiddleware.ts:41`, `src/lib/facility.ts:51-54`). *Seed: fix the guard; make tenancy mandatory middleware-level.*
