## 1. Purpose & scope

Referrals is the SNF discharge-order workflow: the attending physician's **discharge order summary** directing a resident's post-facility care to an external **Home Health Agency (HHA)**. A referral captures the discharge destination, clinical home-service orders, and additional orders on a dynamic clinical form, moves through a doctor-review → in-house e-signature pipeline, is rendered to a certified PDF, and is delivered to the selected agency. The module also owns the **HHA directory** (the agency master data referrals are addressed to).

**In scope:** the referral and agency workflows as implemented in `senior_living_backend` (`/api/referrals`, `/api/agencies`) and surfaced in `senior_living_admin` (the Referrals screen — form generation, agency CRUD, print view, e-signature capture, agency-email delivery) and, as of staging, `senior_living_staffapp` (the **Pending Sign** doctor e-signature queue — the referral half of a combined referral+ACD mobile signing surface).

**Out of scope:** care conferences, IDT reports, and case-manager/doctor schedules (Care Coordination module — [care-coordination.md](./care-coordination.md)); the **advance-care-directive** half of the doctor e-signature story and the ACD entity itself (Clinical Records module — CLIN-FR-19a / CLIN-GAP-09); the care-team designation / `assignedStaff[]` gating backbone that scopes the doctor referral queue (defined in [care-coordination.md §7](./care-coordination.md) and platform-foundation.md PLAT-FR-54 — referenced here, not owned here); the AL-side `/api/care` Outside-Agency wellness flow, whose free-typed `agencyName` bypasses this module's agency directory (Wellness module — referenced only for the referential-integrity gap, §9).

## 2. Personas & surfaces

| Persona | Surface | Role in this module |
|---|---|---|
| Case Manager (staff) | Admin web | Drafts and generates referrals; selects the HHA and the assigned physician |
| Doctor (staff) | Admin web, staff app | Reviews and e-signs referrals (`GET /referrals/my` doctor queue, scoped to the caller's own `assignedPhysician` referrals). **As of staging, the doctor's referral e-signature queue is also reachable natively from the staff app's mobile "Pending Sign" tab** (REF-FR-05a), which replaces My Schedule in the tab bar for doctor-designation users — previously this queue was admin-web-only. |

Primary operating surface: **admin web** — the Referrals screen (`Referrals.tsx`, 1,653 ln) is the single largest care-workflow screen in the product. The staff-app Pending Sign tab is the first (and, for referrals, only) mobile client; the backend `GET /referrals/my` doctor queue serves both.

## 3. Functional requirements (as-built)

- **REF-FR-01 — Referral entity.** A referral binds: facility, resident (ref), `orderDate`, `dischargeTo` (free-text destination, required), `dischargeDate` (required), `homeServices`, `additionalOrders`, `selectedHHA` (ref Agency — **now vestigial on pre-production: still on the schema but never set on create/update, since agency targeting moved to send time via `ReferralSentHistory`, REF-FR-09**), `physicianCertification` {signature S3 key, dateSigned, physicianNamePrint, licenseNumber}, `unsignedPdfUrl`, `signedPdfUrl`, and a write-once `signatureAudit` {doctorCName, signedAt, ipAddress, userAgent}. **As of staging** it also carries `assignedPhysician` (required Staff ref, indexed — REF-FR-03), the `createdBy`/`updatedBy` provenance quartet (REF-FR-03), and **`additionalDocuments[]`** — an embedded `IReferralDocument` sub-schema (`{name, s3Key, mimeType, sizeBytes, uploadedAt}`, own `_id`) holding supplementary files attached to the referral for delivery alongside the order-summary PDF (see the document-CRUD half of REF-FR-09). (`Referral.model.ts`)

- **REF-FR-02 — Dynamic clinical order form.** The referral form is driven by a declarative config (`REFERRAL_FORM_CONFIG`, `config/referralFormConfig.ts` 322 ln): field types `checkbox | yesno | text | textarea` with arbitrarily nested `conditionalFields` keyed by trigger (`checked`/`yes`/`no`).
  - **Home services checklist:** skilledNursing (nests `woundCareRequired` → `woundCareNotes` textarea), physicalTherapy, occupationalTherapy, medicalSocialWorker, speechTherapy, homeHealthAide (booleans).
  - **Additional orders:** dmeRequired (yes/no → `dmeType` equipment text), labWork (yes/no → details textarea). **`pcpFollowUp` was removed on pre-production** (`referralFormConfig.ts`; admin `IReferral.additionalOrders`) — only `dmeRequired` + `labWork` remain.
  - Serialization writes only active branches (`serializeHomeServices`/`serializeAdditionalOrders`); hydration maps legacy keys (`durableMedicalEquipment` → `dmeRequired`, `specificInstruction` → `woundCareNotes`).
  - **New free-form fields (pre-production):** `additionalNotes` (a §5 "Additional Notes" textarea) and `includeMedicationList` (a §7 "Add medication list to the referral" checkbox that folds the client-generated medication-list PDF into the send payload). (`GenerateReferralForm.tsx`; `Referral.model.ts:49,51`)

- **REF-FR-03 — Status machine (centralized + renamed on staging).** The status values were extracted into a single source of truth `REFERRAL_STATUS` (`src/constants/referral.ts`, new) and **renamed**; the schema now imports it and defaults correctly. The staging enum is `Incomplete → Pending Signature → Ready to send → Sent` (typed union), replacing the prior `Draft → In Doctor Review → Doctor Approved → Sent`:
  - `Draft → Incomplete` (`INCOMPLETE`, the corrected default — previously the schema defaulted incorrectly to `In Doctor Review`)
  - `In Doctor Review → Pending Signature` (`PENDING_SIGNATURE`)
  - `Doctor Approved → Ready to send` (`READY_TO_SEND`)
  - `Sent` unchanged (`SENT`, terminal "delivered to agency").
  A one-time data migration (`src/scripts/migrate-referral-status.ts`, new) rewrites existing DB values; **it must be run against each environment before promoting the rename past staging** (§9 O-10).
  - Create with `isDraft: true` → `Incomplete`; **no notification, no PDF**.
  - Create non-draft → `Pending Signature`; fires (fire-and-forget, in parallel): push notifications (REF-FR-06) and unsigned PDF generation (REF-FR-04).
  - Signing (REF-FR-05) → `Ready to send`.
  - Recording a send (REF-FR-09) → `Sent` — the terminal state is **now auto-applied** when a `ReferralSentHistory` entry is created (previously it had to be set manually via PUT; O-1 further resolved).
  - `PUT /api/referrals/{id}` permits arbitrary `status` writes within the enum — **no transition guard** (§9, observation O-2). The referral also carries `assignedPhysician` (Staff ObjectId ref, **required + indexed**) distinct from the care-team-derived attending doctor, plus new provenance fields `createdBy`/`createdByType`/`updatedBy`/`updatedByType` (cName + Cognito group of the creator / last-updater).

- **REF-FR-04 — Unsigned PDF generation.** On non-draft create, `generateAndStoreReferralPdf` renders the discharge-orders HTML (facility display name derived from facilityId, **facility license number from `Config.facilityLicenseNumber`** (optional, new field on Config model), **facility concierge number**, resident name/DOB, **attending physician name resolved from `assignedPhysician` → Staff name** now embedded in the unsigned template, home-services checkboxes, additional orders, agency name) via Puppeteer → S3 `referrals/unsigned/{id}-{ts}.pdf` → CloudFront URL persisted in `unsignedPdfUrl`. The unsigned PDF is treated as the immutable blank form and is never modified. *(Staging: the attending physician is now the explicit `assignedPhysician` field rather than the removed `Resident.doctor` care-team field.)*

- **REF-FR-05 — In-house e-signature.** `POST /api/referrals/:id/sign` (no third-party e-sign vendor):
  1. Client pre-uploads the physician's signature image to S3 (presigned-URL flow; admin UI captures via canvas/base64) and supplies `signatureKey`, `physicianNamePrint`, `licenseNumber`, `dateSigned`.
  2. Server captures `ipAddress` (X-Forwarded-For aware) and `userAgent` from the request.
  3. `signReferralPdf` downloads the signature image, inlines it as a base64 data URL, **re-renders the full discharge HTML with the embedded signature block**, generates a new PDF at `referrals/signed/{id}-{ts}.pdf`, then updates `signedPdfUrl`, `physicianCertification.*`, `status: 'Ready to send'` (staging; formerly `'Doctor Approved'` — REF-FR-03), and writes the immutable `signatureAudit` (doctorCName = authenticated caller).
  4. **No role check** that the signer is a Doctor or the resident's assigned doctor — any authenticated user becomes the audited signer (§9, observation O-3).

- **REF-FR-05a — Staff-app doctor e-signature surface, "Pending Sign" (staging, staff app master HEAD `4aa3849`).** The staff app's MIGRATED (Skilled Nursing) navigation now replaces the **My Schedule** tab with a **Pending Sign** tab for staff whose designation resolves to Doctor (via a new `isDoctorDesignation()` helper — platform-foundation.md PLAT-FR-30a). This is the first mobile surface for either e-signature flow in the platform — both were previously admin-web-only:
  - `PendingSignScreen` lists outstanding documents awaiting the doctor's signature — referrals (this section, via the existing `GET /referrals/my` doctor queue) and advance care directives (clinical-records.md `GET /advance-care-directives/doctor/pending-signatures`, CLIN-FR-19a) in one combined queue.
  - `PendingSignDetailScreen` renders the document detail.
  - `SignedPdfPreviewScreen` generates a **client-side signed PDF** (via the new `jspdf`/`pdf-lib` dependencies) with support for **multiple signatures per page**, before submitting through the existing signing endpoints — `POST /api/referrals/:id/sign` (REF-FR-05) for referrals, `PUT /api/advance-care-directives/:id/sign` (CLIN-FR-19a) for ACDs.
  This is a client surface only — it consumes the existing REF-FR-05 and CLIN-FR-19a endpoints and does not add a new backend contract. The role-gate weakness noted in observation O-3 (no server-side check that the signer is a Doctor) therefore applies identically regardless of whether the sign action originates from admin web or this new mobile surface.

- **REF-FR-06 — Referral & ACD review notifications (rebuilt on staging).** The referral review push was rebuilt into a dedicated `referral.notification.service.ts` → `notifyDoctorOfReferralReview()`, which fires only when the referral status is `Pending Signature` (REF-FR-03). Title `"Referral Awaiting Review"`; body `"A discharge referral for {resident} is awaiting your review and signature."`; FCM data `type: 'REFERRAL_IN_DOCTOR_REVIEW'`. Recipient resolution cascades: the referral's `assignedPhysician` → the resident's assigned Doctor/Physician → the facility Admin `pushToken`. A sibling `advanceCareDirective.notification.service.ts` → `notifyDoctorOfAcdSignatureRequest()` fires when a directive is created with `isNeedSignature: true` (title `"Signature Required"`; body `An advance care directive "{title}" for {resident} requires your signature.`; FCM `type: 'ADVANCE_CARE_DIRECTIVE_SIGNATURE_REQUIRED'`) — the ACD-side companion that populates the same staff-app Pending Sign queue (REF-FR-05a; clinical-records.md CLIN-FR-19a).

- **REF-FR-07 — Listing & doctor queue.**
  - `GET /api/referrals` — facility-wide, paginated, filters residentId/status; search spans resident first/last name, **assigned-doctor name**, and agency name (multi-collection regex then `$in`); response decorates resident with signed profile-picture URL and resolved doctor name/cName.
  - `GET /api/referrals/my` — the doctor review inbox: scope = referrals whose `assignedPhysician` resolves to the **caller's own Staff `_id`** (`referral.controller.ts:301-314`); same search/status filters. *(Staging: re-scoped from the removed `Resident.doctor` care-team field to the explicit `assignedPhysician` ref.)* The admin `GenerateReferralForm` filters the staff dropdown to **physicians only** when selecting `assignedPhysician` (`referral-form.tsx`, production 2026-06-30). This is the same endpoint the staff-app Pending Sign tab (REF-FR-05a) consumes for its referral section.
  - Update = partial `$set` (now also accepts `assignedPhysician`); delete = **hard delete** (`findOneAndDelete`). The admin UI wires a delete (`use-delete-referral.ts`, `DELETE /referrals/{id}`).

- **REF-FR-08 — Agency directory CRUD.** `Agency`: name, email, countryCode+phone, **`faxNumber`** (new on staging), address (street/city/state/zip), `specialties[]`, status `Active|Inactive` (default Active), facility-scoped. `GET/POST /api/agencies`, `PUT/DELETE /api/agencies/{id}`; list supports search + status filter. **Hard delete; no duplicate-name guard; auth-only (no role gate).** Consumed by referrals (`selectedHHA`); referral PDFs print the agency name; referral search matches agency names; the agency `email` is the recipient for referral-email delivery (REF-FR-09). Agency CRUD UI lives inside the Referrals screen (not the rehab/wellness Outside Agency screen, whose `agencyName` remains a free string — referential-integrity gap noted in client-admin-web.md §4.4).

- **REF-FR-09 — Record a send (`ReferralSentHistory`) — staging.** The prior SES-email delivery (`POST /api/referrals/send-referrals-emails` → `SendRawEmailCommand`) is **superseded on staging** by a "record, then fax" model. `POST /api/referrals/:id/sent-history` (multipart, optional medication-list file) creates one **`ReferralSentHistory`** document per Send-to-Agencies action (`referralSentHistory.service.ts` → `createReferralSentHistoryEntry`; new collection, replacing the old embedded `Referral.sendHistory[]`). Each entry **snapshots the send at that instant** so later agency/document edits do not rewrite history: `agencies[]` (agencyId + `agencyName` + `agencyFaxNumber` frozen), `documents[]` (frozen `name`/`s3Key`/`mimeType`/`sizeBytes`), `medicationListIncluded`, and a lifecycle `status` (`REFERRAL_SENT_HISTORY_STATUS`: `PENDING → PROCESSING → COMPLETED | FAILED | PARTIAL`). The service snapshots the order-summary PDF from existing S3 metadata, uploads the **client-generated medication-list PDF** when supplied, and copies the referral's `additionalDocuments[]` metadata; it then sets the parent `Referral.status = Sent` (REF-FR-03). **This endpoint only *records* the send — it does not itself fax.** The admin web wires "Send to Agencies" to this endpoint (document CRUD + agency multiselect in the send-referral modal). Send validation still requires residentName, dateOfBirth, attendingPhysician, orderDate, dischargeDate, selectedAgency, physicianSignature, dateSigned.

- **REF-FR-09a — Fax dispatch via WestFax — staging.** The actual agency delivery is fax, via a new **WestFax** integration. `POST /api/fax/westfax/send { referenceId }` (`referenceId` = a `ReferralSentHistory` `_id`; `westfaxSend.controller.ts`, mounted on `fax.routes.ts`, guarded by `facilityMiddleware` + `authMiddleware` unless `FAX_LOCAL_BYPASS=true`) responds **202 immediately**, then a background `dispatchFaxes()` loops **agencies × documents**, downloads each document from S3 once, and faxes it to the agency `faxNumber` via `sendFaxWestFax()`. Per-vendor auth is resolved per-facility from `IntegrationAvailable` (`name: 'westfax'`; base64-decoded clientId/clientSecret → username/password, `productId` from `externalId` — `resolveWestFaxConfig(facilityId)`). Each individual fax is recorded in a new **`FaxLog`** collection (`{referralSentHistoryId, agencyId, documentS3Key, jobId, status, faxDetails, errorMessage}`); the parent `ReferralSentHistory.status` is rolled up to `COMPLETED` / `FAILED` / `PARTIAL` when the loop finishes. Status callbacks arrive at the WestFax webhook (REF-FR-09b). The generic **Documo** fax integration (`POST /api/fax/send`, platform-foundation.md §6) still exists but is a separate ad-hoc path — the referral-send flow now goes through WestFax, not Documo or SES email. (`integrations/westfax/westfax.service.ts`, `controllers/westfaxSend.controller.ts`, `models/FaxLog.model.ts`)

- **REF-FR-09b — WestFax delivery webhook — pre-production.** `GET /webhooks/westfax?jobId=&productId=&dir=` (plus a `GET /webhooks/westfax/ping` health check; `westfax.webhook.controller.ts` → `handleWestfaxWebhook`, mounted outside `/api`) ACKs 200, then looks up the matching `FaxLog` by `jobId`, re-fetches the fax details from WestFax (`getFaxDetails()`), and updates the `FaxLog` status. The callback URL is now **config/host-driven** (`buildCallbackUrl(baseUrl)`) rather than a hardcoded staging literal (O-9 resolved). **This webhook still has no authentication and no signature verification** — anyone reaching the URL can flip a `FaxLog` status; a production-promotion blocker (§9 O-8).

- **REF-FR-09c — Send dedup & fax retry — pre-production.** Two operational refinements landed with the promotion. **Dedup:** `referralSentHistoryDedup.service.ts` (`computeAlreadySentKeysByAgency`) walks every prior send batch and skips any (agency, document) pair already sent — keyed `ORDER_SUMMARY` / `MEDICATION_LIST` / `ADDITIONAL:<s3Key>`, counting **any** prior attempt regardless of fax outcome — so re-sending a referral only faxes what an agency has not already received; if nothing is new for any selected agency, no `ReferralSentHistory` is written and the referral status is untouched. The admin send modal previews this per document as a hover tooltip ("Already sent to all" vs the list of agencies that would newly receive it) via `POST /referrals/:id/sent-history/preview`. **Retry:** `POST /api/fax/westfax/retry` (accepts `[{referenceHistoryId, faxIds[]}]`, 202) re-fetches each agency's current fax number, re-downloads from S3, re-sends, and increments `FaxLog.retryCount`/`lastRetryAt`, rolling the parent `ReferralSentHistory.status` to `PARTIAL`/`COMPLETED`. The admin **Fax Delivery History** modal surfaces per-document DELIVERED/FAILED/PENDING status (recomputed live from `FaxLog`), a per-agency retry action with optimistic feedback, and 7-second polling until nothing is PENDING.

- **REF-FR-10 — Discharge-date backdating window (pre-production, NEW, v1.6).** A referral's Discharge Date can be backdated only within a facility-configurable window: `Config.dischargeDateMaxPastDays` (optional; absent = backend default `DISCHARGE_DATE_MAX_PAST_DAYS = 28`, `constants/referral.ts:21`), enforced server-side at submit time (`referral.validation.service.ts`). The admin `GenerateReferralForm` mirrors the same window client-side as the date-picker's minimum selectable date and an inline validation message ("Discharge date cannot be more than N day(s) in the past"), computed against the facility's configured timezone (`getCurrentDateInTimeZone`) rather than the browser's local date. (`senior_living_admin` `GenerateReferralForm.tsx`; `senior_living_backend` `config.model.ts:179-182,626-630`, `referral.validation.service.ts`)

## 4. Business rules & policies

| # | Rule | Source |
|---|---|---|
| REF-BR-1 | A draft referral produces no notification and no PDF; only non-draft creation triggers the doctor-review pipeline. | `referral.controller.ts` create flow |
| REF-BR-2 | The unsigned referral PDF is immutable; signing always produces a **new** PDF with the signature block re-rendered into the document. | `referral.sign.service.ts` |
| REF-BR-3 | `signatureAudit` (doctorCName, signedAt, IP, user-agent) is written once at signing and is immutable thereafter. | `Referral.model.ts` |
| REF-BR-4 | The doctor referral queue is scoped by the referral's explicit `assignedPhysician` Staff ref, not a care-team designation field — consumed identically by admin web and the staff-app Pending Sign tab (REF-FR-05a). | `GET /referrals/my`; REF-FR-05a |
| REF-BR-5 | Agency deactivation is a status flag (`Inactive`), but agency delete is hard — referrals referencing a deleted agency dangle. | backend §6a |
| REF-BR-6 | Multi-tenancy: every route is facility-scoped via the `x-facility-id` header (`facilityMiddleware`); all queries filter by facilityId. | backend §0 |

## 5. Notifications & real-time behavior

| Trigger | Channel | Recipients | Gate |
|---|---|---|---|
| Referral reaches `Pending Signature` (non-draft create) | FCM | `assignedPhysician` → resident's Doctor → Admin `pushToken` (first match) | `notifyDoctorOfReferralReview()` — fires only on `PENDING_SIGNATURE` (`type: REFERRAL_IN_DOCTOR_REVIEW`) |
| ACD created with `isNeedSignature` | FCM | resident's Doctor (ACD companion) | `notifyDoctorOfAcdSignatureRequest()` (`type: ADVANCE_CARE_DIRECTIVE_SIGNATURE_REQUIRED`) |
| Fax delivery result (WestFax callback) | none (webhook → `FaxLog` status only) | — | `handleWestfaxWebhook` updates `FaxLog`/`ReferralSentHistory` status; no resident/staff push on delivery result today (§9 O-11) |

Notification fan-out is FCM-only with history persistence; no socket events exist for this module. Referral/ACD e-signature pending-queue items pushed via the care-coordination notification channel are what populate the staff-app Pending Sign tab (REF-FR-05a) on next fetch — there is no dedicated real-time channel for the Pending Sign queue itself.

**Resident-side caveat:** the SN resident app's notification center renders the FCM-backed feed but implements no mark-as-read and no tap-through navigation (client-resident-app-sn.md §3.10) — referral pushes land as inert feed entries on the resident device.

| **WestFax (fax)** | Referrals — agency delivery (staging) | The as-built agency-delivery channel (REF-FR-09a/b). `POST /api/fax/westfax/send { referenceId }` background-dispatches each `ReferralSentHistory` document to each agency `faxNumber`; per-fax `FaxLog`; `GET /webhooks/westfax` status callback. Per-facility auth from `IntegrationAvailable(name:'westfax')`. (`integrations/westfax/`) |
| **AWS SES (email)** | Referrals — **superseded on staging** | The prior `POST /referrals/send-referrals-emails` SES path (password-protected PDF via `SendRawEmailCommand`) is superseded by the WestFax fax pipeline for agency delivery. SES remains the platform email transport for other flows (platform-foundation.md). |
| **Documo (fax)** | Platform-level (unrelated to referrals) | Generic `POST /api/fax/send` outbound fax (`integrations/documo/`); a separate ad-hoc fax path — **not** the referral-send channel (WestFax is). (platform-foundation.md §6, §9 fax-bypass gap) |
| **FCM** | Referral notifications | Token harvested implicitly from resident-app request headers; per-facility config gating |

## 7. Permissions & access control

**Doctor-queue scoping keys on the referral's explicit `assignedPhysician` ref** — not a care-team designation field, and not the removed `Resident.doctor` field (REF-FR-07). The broader `Resident.assignedStaff[]` care-team model that governs resident↔staff scoping across the platform is defined in [care-coordination.md §7](./care-coordination.md) / platform-foundation.md PLAT-FR-54.

**Route-level enforcement as-built:**

| Surface / route group | Gate |
|---|---|
| Referrals (all routes incl. `POST /:id/sign`) | `authMiddleware` only — **no role middleware**; signer identity not validated as Doctor (§9, O-3). This gap is unchanged by the new staff-app Pending Sign client (REF-FR-05a) — it calls the same unguarded endpoint. |
| Agencies CRUD | `authMiddleware` only — no role gate, hard delete |
| Admin web frontend | The Referrals screen has **no `usePageAccess` gate** — it relies on nav-level filtering + backend enforcement only; direct state navigation renders it regardless of page permission (client-admin-web.md §4.4) |

Multi-tenant isolation (facilityId filter from `x-facility-id`) **is** consistently enforced across the module even where role gates are missing.

## 8. Product-split notes

- Referrals are a **SNF-flavored** construct: discharge referrals to HHAs with physician certification serve skilled-nursing workflows (backend §8.3). Exposure in the admin web is governed by the facility-pages API (Filter 1), not code conditionals. The staff-app Pending Sign tab (REF-FR-05a) is likewise only reachable by doctor-designation staff, who exist predominantly in SNF facilities under the current designation model.
- The **agency directory is shared infrastructure across the split**: managed here (Referrals screen) but referenced as a free-typed string by the AL-side Outside Agency wellness flow — any unified product must make `agencyName` a foreign key (client-admin-web.md §4.4; §9 O-4).

## 9. Observations & candidate gaps

Evidence-backed defects, mismatches, and half-built areas a forward PRD must resolve:

- **O-1 — `Sent` status — resolved (pre-production).** The status enum is centralized (`REFERRAL_STATUS`) and `Sent` is **auto-applied** when a `ReferralSentHistory` entry is created (REF-FR-09), so the terminal state no longer depends on a manual `PUT`. The as-built delivery mechanism is now **WestFax fax** (REF-FR-09a), not the prior SES email. *Residual: the fax dispatch is a separate call (`POST /api/fax/westfax/send`) — a referral can be marked `Sent` (history recorded) without the fax loop having actually succeeded; true delivery state lives on `FaxLog`/`ReferralSentHistory.status` (`COMPLETED`/`FAILED`/`PARTIAL`), which the referral's own `status` does not reflect (see O-11). Pre-production added a **retry** path (`POST /api/fax/westfax/retry`) and **live status recompute** from `FaxLog` to at least make failed faxes recoverable and visible in the Fax Delivery History UI.*
- **O-2 — No referral status-transition guard.** `updateReferral` accepts arbitrary enum statuses; a Doctor-Approved referral can be silently reverted to Draft via PUT (backend §3 status machine).
- **O-3 — Unverified referral signer — largely addressed (v1.5, pre-production).** Two layers now gate signing. (1) The canonical signing endpoint moved to the **unified `/api/signatures` service** (`PUT /:id/sign`, clinical-records.md CLIN-FR-19b), whose routes carry **`requireAnyStaffDesignation([DOCTOR, PHYSICIAN])`** — so only a doctor-designation staff member can sign any document kind (directive/referral/medication-list). (2) The **doctor pending-signature queue** and the **signing-authorization branch** additionally scope by the referral's `assignedPhysician` (403 unless `referral.assignedPhysician === staffDoc._id`; commits `2253b4f5`, `a23408db`) — so the signer must be the physician the referral is addressed to. **Residual:** the legacy `POST /referrals/:id/sign` and `/api/advance-care-directives/:id/sign` aliases are retained for the doctor mobile app; confirm they route through the same designation gate (they share handlers, so they should) and retire the aliases once clients migrate. The IP/UA `signatureAudit` records the signer as before. Net: the earlier "any authenticated user can sign" exposure is effectively closed on the canonical path.
- **O-4 — Agency referential integrity.** Agencies are hard-deleted with no duplicate-name guard and no role gate; referrals hold `selectedHHA` refs that can dangle; the wellness Outside Agency flow bypasses the directory entirely with free-text `agencyName` (backend §6a; client-admin-web.md §4.4).
- **O-5 — Referral draft accepts `physicianCertification` from the client** at create time even though signing overwrites it (intended only as name/license pre-fill) — a spoofable-looking field until signed (backend §10.11).
- **O-6 — `MOCK_AGENCIES` scaffolding** still in source beside the live agencies API (`Referrals.tsx`). The mock-driven `GenerateReferralModal` composer that uses it is **mounted but never opened — confirmed dead/unreachable code** on pre-production (its open state is never set true); it should be deleted. A referral **delete UI exists** (`use-delete-referral.ts` → `DELETE /referrals/{id}`), so the prior "no delete/archival UI" half of this gap is resolved.
- **O-7 — No frontend permission gate** on the Referrals screen in the admin web (`usePageAccess` absent); combined with the missing backend role gate on referral routes (§7), referral access control is effectively "any authenticated user in the facility" (client-admin-web.md §4.4). *(This is the referral facet of the broader admin-web page-gate gap tracked in care-coordination.md §9 O-7.)*

- **O-8 — WestFax webhook is unauthenticated and unverified — STILL OPEN (pre-production).** `GET /webhooks/westfax` (REF-FR-09b) performs no auth and no signature/HMAC verification of the callback; anyone who can reach the URL can post `jobId/productId/dir` and flip a `FaxLog` status. This shipped to pre-production **unfixed** — it is a **production-promotion blocker**: a delivery-status webhook that mutates fax records must verify the caller before this reaches `production`. *(Mirrors the unauthenticated PCC/`pcc-sync` surfaces — clinical-records.md CLIN-GAP-19; both are the same "webhook/ops endpoint outside `/api` with no verification" pattern.)*
- **O-9 — WestFax callback URL — RESOLVED (pre-production).** The callback URL is no longer hardcoded to the staging host: `westfax.service.ts` now exposes `buildCallbackUrl(baseUrl)` and `dispatchFaxes`/`retryOneFax` pass a `baseUrl` resolved per environment, so faxes dispatched from pre-prod/prod call back to their own host. (The former `https://staging-api.sal.shashitech.com/...` literal is gone.) Only the **webhook-auth** half of the old combined gap remains (O-8).
- **O-10 — Status-rename migration is a manual script.** The `Draft/In Doctor Review/Doctor Approved` → `Incomplete/Pending Signature/Ready to send` rename (REF-FR-03) is a stored-value change; `src/scripts/migrate-referral-status.ts` (which backs up to a `referrals_migration_backup_YYYYMMDD` collection first) must be run against each environment's DB before promotion, or referrals persisted under the old labels fall outside the new typed enum. No automatic migration runs at boot. This was necessarily run against `pre-production` as part of the promotion; **it must still be run against `production` before that promotion**, and is the kind of manual step that belongs in the release runbook, not a developer's memory.
- **O-11 — Referral status does not reflect fax delivery outcome.** `Referral.status = Sent` is set at *record* time (REF-FR-09), independent of whether the WestFax dispatch (REF-FR-09a) actually delivered. Failed/partial fax outcomes live only on `ReferralSentHistory.status` / `FaxLog`, with no resident/staff notification on a delivery failure and no reconciliation back to the referral. A dispatcher looking at a `Sent` referral cannot tell a delivered fax from a failed one without opening the send history.
- **O-12 — WestFax + onboarding paths log via `console.*`.** The WestFax service and the shared PCC onboarding use `console.log/error` rather than the platform structured logger — consistent with the repo-wide logging-hygiene gap, but notable on a new PHI-adjacent delivery path.

> **Related cross-module gaps:** the ACD half of the doctor e-signature story (CLIN-GAP-09, clinical-records.md §9) and the fax-guard bypass `FAX_LOCAL_BYPASS` (platform-foundation.md §7) touch the same signing / delivery surfaces as this module.
