## 1. Purpose & scope

Clinical Records covers the three resident-health document/data domains that the platform stores and surfaces today:

1. **Medications** — a per-resident medication list with two data sources: manual self-entry by the resident, and an automated, encrypted sync of medication orders from **PointClickCare (PCC)**, the facility's LTC/SNF EHR. Includes a printable medication-list PDF for staff and a read-only list in the resident app.
2. **Lab integration** — inbound webhook ingestion of lab results from **Lemedix / CrelioHealth** (patient registrations and signed report PDFs with structured analyte values), resident-facing report viewing with search, and a separate self-service **Test Results** document locker for manually uploaded files.
3. **Advance Care Directives (ACD)** — a per-resident document locker for directive files (living will / POLST-type), uploaded by the resident from the mobile app either as a picked PDF or via an in-app image-scan-to-PDF flow.

**In scope:** data models, sync/ingestion flows, encryption-at-rest behavior, PDF generation, resident/family/staff read surfaces, and the access-control behavior as built.

**Out of scope (separate modules):** Referrals & physician e-signature, IDT reports, Care Conferences, Rehab/therapy scheduling, rehab messages, chat. These are clinically adjacent but documented in their own module PRDs. The **use** of `Resident.assignedStaff[]` for chat eligibility, notification fan-out, and "my residents" scoping is documented in care-coordination.md (CARE-FR-63/BR-7); this module documents only the newest **writer** of that array (PCC practitioner sync, §3F).

**Key as-built characterization:** this module is predominantly a *records and visibility* capability, not a clinical-workflow capability, **with two exceptions**: PCC-driven admission (CLIN-FR-20d, since 2026-07-10) automates resident onboarding end-to-end rather than merely alerting a manager, and **PCC practitioner sync (CLIN-FR-28 series, since 2026-08-28) automatically assigns/unassigns care-team staff** rather than only storing physician records for display. Aside from those two, there is still no medication administration record (eMAR), no adherence tracking, no lab-result alerting, no directive e-signature or attestation on the resident-upload path. Several stored data structures (structured lab analytes, lab patient registry) are write-only today — captured but unsurfaced.

## 3. Functional requirements (as-built)

### 3A. Medications

- **CLIN-FR-01 — Resident medication list (self-view).** An authenticated resident retrieves their own medication list. *(Staging client change:* the skilled-nursing resident app now reads its own list via `GET /api/medications/resident?cName=&status=` (passing the resident's own cName, optional `MedicationStatus` filter; `health/index.tsx:529`) instead of the self-scoped `GET /api/medications/`. Both backend routes exist — `/` (self, auth-only) and `/resident` (by cName, no role middleware — CLIN-GAP-03).) Default visibility remains `status: 'ACTIVE'`. Family members authenticated against a linked resident receive that resident's list via username normalization. *(Backend §1; SN app §3.2 Medications.)*

- **CLIN-FR-02 — Medication display shaping.** List reads decrypt PCC `medication_data` per record and reduce it to a display object: medication/generic name; strength summary (`dose doseUOM • route • scheduleType`); directions ("Take {dose} {doseUOM} {route} {frequency}"); start/end dates formatted in the PCC integration's configured timezone (default `America/Los_Angeles`); prescribing doctor; narcotic flag. Manual-entry records surface their legacy fields directly (medicationName, strength, route, frequency, prescribingDoctor, startDate). The resident app renders each item as a summary row (name; strength • route • frequency) with an expandable detail panel and a list-level "last updated" date from `lastUpdatedAt`.

- **CLIN-FR-03 — Manual medication CRUD (self-service only).** `POST /api/medications/` creates a manual entry for the **caller's own** cName; `GET/PUT/DELETE /:id` are filtered `{_id, cName: caller}` so manual record management is strictly self-service. Manual status values are limited by validation to `ACTIVE | INACTIVE | COMPLETED`.

- **CLIN-FR-04 — Soft delete.** Deleting a medication sets `status: 'INACTIVE'`; records are never hard-deleted via the API.

- **CLIN-FR-05 — Staff medication view by resident.** `GET /api/medications/resident?cName=&status=` returns any resident's medications within the caller's facility (status filter defaults to ACTIVE). As built, this route has **no role middleware** — see CLIN-GAP-03.

- **CLIN-FR-06 — Medication-list PDF.** `GET /api/medications/resident/pdf?cName=` generates a printable medication list (Puppeteer HTML→PDF): resident name, room, DOB, physician, generated date, and a table of name / strength / type / route / start date / directions. **Pre-production changes:** each medication's `medication_data` schedules are now **flattened into individual rows** (a med with N schedules renders N rows, not one collapsed row); the template was re-branded/re-termed (title "Medical Receipt"→**"Medication List"**, "Patient Name"→"Resident Name", "Doctor Name"→"Physician", right-side branding block removed), and the physician is now resolved from the `PHYSICIAN` staff designation, joining all matching names. This PDF is also the one folded into the referral send payload when `includeMedicationList` is set (referrals.md REF-FR-09). **v1.5:** the `Medication` model gained `strength` and `prescribingDoctor` string fields (`Medication.model.ts:21,24`), backfilled onto existing records by one-off scripts (`SCRIPT-bulk-updated-medication-prescribingDoctor`, `added-updated-strengh-medication-data`); these feed the strength column and the per-medication physician on the PDF and the referral medication-list document.

- **CLIN-FR-07 — PCC medication sync (webhook-driven).** PCC webhooks (`/webhooks/pcc`) handle `medication.add / update / discontinue / strikeout / cancelDiscontinue`. On each event the system: (a) resolves the resident by `pcc_patientId` + `pcc_orgUuid` (case-insensitive; unmatched events are skipped); (b) fetches the resident's full medication list from the PCC API (paged 200/page; OAuth client-credentials over mTLS; per-client rate limiting; token cached with a 5-minute expiry buffer); (c) encrypts every payload field (CLIN-FR-08); (d) upserts records keyed `{facilityId, cName, orderId}`. **This same fetch→encrypt→upsert pipeline is now also invoked directly from resident onboarding** — see CLIN-FR-20d. **Resilience (pre-production):** each PCC read is wrapped so a **401** invalidates the cached token (by clientId), re-fetches once, and retries once (second failure rethrown); **5xx** responses retry with backoff (`PCC_MAX_5XX_RETRIES`, default 2) then throw `PccServerError`, which medication sync catches and **returns empty** rather than failing the webhook — so a transient PCC outage degrades to "no update this event" instead of an errored handler. **This OAuth/mTLS pipeline (`pcc.service.ts`) is unchanged by the 2026-08-28 practitioner-sync pass — practitioner sync uses its own, separate, newly-added copy of the token cache and https agent (`pcc.core.ts`); see CLIN-GAP-24.**

- **CLIN-FR-08 — Per-resident envelope encryption of PCC data.** Every value in a synced `medication_data` payload is AES-encrypted with a per-resident data key, KMS-wrapped and stored on `Resident.pcc_medication_wrappedKeyB64`. The key is generated on first write and cached in-process. Field **keys** remain visible; field **values** are ciphertext at rest. Read paths request the key in `readonly` mode; if no key exists or decryption fails, the record degrades to an empty `medication_data` (graceful PHI redaction rather than a 500). **A second, resource-agnostic PCC envelope key was introduced 2026-08-28** (`Resident.pcc_wrappedKeyB64`) for practitioner data (CLIN-FR-28) — the two keys are independent and neither migrates the other; medication sync keeps using its own dedicated key unchanged.

- **CLIN-FR-09 — PCC order lifecycle statuses.** Medication status enum: `ACTIVE | INACTIVE | COMPLETED | UPDATED | PENDING | DISCONTINUED | INITIAL | STRIKEOUT | CANCEL_DISCONTINUE`. The first three serve the manual path; the rest mirror PCC order lifecycle via a status-mapping function. Behavior on specific events: *discontinue* stores a `discontinueDate`; if an orderId disappears from the PCC list, the local record is marked with the event's terminal status (`DISCONTINUED` / `STRIKEOUT` / `CANCEL_DISCONTINUE`); *update* events delete-then-reinsert the order.

### 3B. Lab integration & test results

- **CLIN-FR-10 — Lab patient registration ingestion.** `POST /webhooks/lemedix/patient-registered` stores a `LabPatient` record (demographics, insurance details array, referralId, raw payload). Facility resolution uses the `LEMEDIX_FACILITY_ID` env var (single-account mapping for the pilot facility), falling back to the CrelioHealth `org_id`. **LabPatient records are never linked to a Resident and have no read API** — a write-only registry today (see CLIN-GAP-07).

- **CLIN-FR-11 — Lab report ingestion.** `POST /webhooks/lemedix/report-submit`: (a) resolves the facility via `IntegrationAvailable.externalId === labId` (multi-tenant capable); (b) matches the resident by contact data — `$or` over payload phone fields (`Patient Contact`, `Patient Alternate Contact`, `Contact No`) and `alternateEmail` against `Resident.phone/email`; facility mismatch or no match → webhook ignored; (c) decodes the `reportBase64` PDF and uploads it to S3 under `lab-reports/{centreReportId}-{ts}.pdf` (the base64 blob is excluded from the stored raw payload); (d) creates a `LabReport` linking `residentId`/`cName`/`integrationId`, with report metadata (sampleId, isSigned, branch) and structured `reportFormatAndValues` — per-analyte value, `highlight`/`critical` flags, gender-specific reference bounds, unit. A catch-all `POST /webhooks/lemedix/` also routes to report handling (logged as unknown event). Webhooks ACK 200 immediately and process asynchronously.

- **CLIN-FR-12 — Resident lab-report list.** `GET /api/lab-reports/` returns the authenticated resident's own reports (`{cName, facilityId}` filter) with optional `search` (testName regex) and `reportDate` (UTC day window). Response items: testName, patientName, S3 key plus presigned `signedUrl`, formatted report date. The SN resident app renders this as the **Test Results** screen with debounced server-side search and infinite scroll; tapping opens the PDF in-app (`react-native-pdf`), titled by test name. View-only — no download/share/sign.

- **CLIN-FR-13 — Staff lab-report view by resident.** `GET /api/lab-reports/:residentId` returns a specific resident's reports (resident resolved by `_id` within the caller's facility). No role middleware as built — see CLIN-GAP-03.

- **CLIN-FR-14 — Structured analytes stored, not surfaced.** `reportFormatAndValues` (including critical flags and reference ranges) is persisted on every LabReport but **no endpoint exposes it** — only the PDF link is surfaced. This is the latent foundation for lab trends / critical-value alerting (see CLIN-GAP-08).

- **CLIN-FR-15 — Test Results document locker (manual uploads).** `/api/test-results` is a self-service per-cName file locker, distinct from ingested LabReports: multipart `POST /` (S3 `test-results/` folder; name defaults to filename sans extension), `GET /` own active records with name/filename regex search and presigned URLs, `PUT /:id` replace file and/or rename, `DELETE /:id` soft delete (`isActive: false`). All operations scoped `{facilityId, cName: caller}`; `createdBy`/`updatedBy` audit fields maintained.

### 3C. Advance care directives

- **CLIN-FR-16 — Directive document locker.** `/api/advance-care-directives` stores per-cName directive files (pdf/image) in S3 under `advance-care-directives/`, with optional title (defaults to filename), soft delete via `isActive`, and `createdBy`/`updatedBy` audit fields. Self-service CRUD is scoped `{facilityId, cName: caller}` (same pattern as Test Results).

- **CLIN-FR-17 — Resident upload flow (PDF pick or scan-to-PDF).** The SN resident app's "+ Add" flow offers two paths: (a) pick an existing **PDF** via the document picker (PDF type only); (b) **scan** — capture one or more images via the camera/image picker, converted client-side into a single PDF (jsPDF + blob-util) before upload. Submission requires a title and a selected document; upload is multipart `POST /api/advance-care-directives`; success/failure routes to the shared confirmation screen. **There is no e-signature, witnessing, or attestation flow — upload-only** (see CLIN-GAP-09).

- **CLIN-FR-18 — Resident directive viewing.** The app lists the resident's directives (title, fileName, createdAt, paginated); tap opens the in-app PDF viewer. *(2026-08-21: the in-app PDF viewer's `trustAllCerts` prop, previously `true` on this and the lab/test-result viewer — an MITM-exposure risk noted only in the pre-PRD codebase analysis, never promoted to a tracked gap ID — is now `false` on both. Resolved, not an open item.)*

- **CLIN-FR-19 — Staff directive view (role-guarded).** `GET /api/advance-care-directives/resident/:residentId` allows viewing a resident's directives only when the caller `isStaffOnlyRequest` **or** is the resident themself. This is the strongest-guarded clinical-records staff read — notably stricter than the medication and lab staff reads (the model the gaps in CLIN-GAP-03 should converge to).

- **CLIN-FR-19a — Staff-added directives & doctor e-signature (staging).** Three new endpoints add a clinician-side ACD authoring + sign flow distinct from the resident upload-only path:
  - `POST /api/advance-care-directives/staff` — a **staff-only** (`isStaffOnlyRequest`, else 403) create that records `createdBy`/`updatedBy` as the staff cName, letting a clinician attach a directive on a resident's behalf (`advanceCareDirective.controller.ts:99-157`).
  - `GET /api/advance-care-directives/doctor/pending-signatures` — the **Doctor queue**: the caller must resolve to an `active` Staff with designation `Doctor` (else 403/404), and the response gathers pending-signature directives **and** referrals for residents whose `assignedStaff[]` contains the doctor's cName (`assignedStaff: { $in: [doctorCName] }`) — i.e. the doctor's assigned residents under the unified care-team model (`:495-565`).
  - `PUT /api/advance-care-directives/:id/sign` — the doctor signs a directive (multipart, signature file), promoting it from pending. This is the directive analogue of the referral in-house e-signature (referrals.md REF-FR-05) and is the first ACD **attestation** flow — narrowing CLIN-GAP-09 for the staff-authored path (the resident upload path remains signature-free). **As of staging, this queue is also reachable from the staff app's mobile "Pending Sign" tab (referrals.md REF-FR-05a)** — previously admin-web-only.

- **CLIN-FR-19b — Unified physician signature service (pre-production).** The doctor pending-signature queue was extracted into its own domain at **`/api/signatures`** and now serves **three document kinds** behind one contract: `GET /api/signatures/pending` (every document awaiting this physician's signature) and `PUT /api/signatures/:id/sign` (sign one document, `:id` = the row's `_id` whichever kind it is). The `type` discriminator is **`directive | referral | medication-list`** — the queue had already merged referrals before the referral **medication list** (referrals.md REF-FR-05) joined it as a third kind. **Both routes are gated by `requireAnyStaffDesignation([DOCTOR, PHYSICIAN])`** — so the canonical signing endpoint is now role-restricted to physicians (this **narrows referrals §9 O-3**, which flagged the unguarded signer). The handlers still physically live in `advanceCareDirective.controller.ts` (a mechanical relocation is deferred), and the identical routes under `/api/advance-care-directives` are kept as **deprecated aliases** so the doctor mobile app (its own release cadence) keeps working — retire once every client has moved. (`signature.routes.ts`; `advanceCareDirective.controller.ts` `getDoctorPendingSignatures`/`signAdvanceCareDirective`)

- **CLIN-FR-25 — Consent Forms (resident + family co-signing) (pre-production, NEW).** A resident-consent document with a multi-party e-signature flow, distinct from the physician-attestation flows above (this is resident/family self-signing, not doctor sign-off). Model `ConsentForm` (`{facilityId, residentId, residentName, signedDate, residentSignature (base64), signers[], signedFamilyMembers[], pdfS3Key, residentSignedStatus, status}`); status walks **`Pending → PartialSigned → Signed`**.
  - **Create + resident sign:** `POST /api/consent-forms` creates the form with the resident's signature captured (admin uses a dependency-free `<canvas>` `SignatureCanvas` emitting a base64 PNG); `residentSignedStatus` is set to `Signed` on creation, independent of family statuses.
  - **Family co-sign:** each nominated family member (`signers[]`) signs afterward via `POST /api/consent-forms/sign`; their signature is stored on `signedFamilyMembers[]` and **the PDF is regenerated and overwritten in S3** (`pdfS3Key`) so it accumulates all signatures. `status` becomes `PartialSigned` until all sign, then `Signed`.
  - **Read:** `GET /api/consent-forms?residentId=` (latest form for a resident), `GET /api/consent-forms/:id`, `POST /api/consent-forms/pdf` (family-member PDF).
  - **Side effect:** in the admin UI, signing a consent form **optimistically grants the co-signing family members app/portal access** (`isAuthorizedAppAccess`/`hasPortalAccess`) — consent and app-access provisioning are coupled in the flow. The resident record carries `hasConsentForm` / `hasUnviewedSignedDocument` flags for surfacing. Backed by the generic `/api/signatures` service infrastructure. ### 3D. PCC patient lifecycle webhooks

> Companion to the PCC *medication* sync (§3A, CLIN-FR-07) and the *practitioner* sync (§3F, CLIN-FR-28 series). ### 3F. PCC practitioner sync & automatic care-team assignment (new, 2026-08-28)

> Third PCC event pattern alongside status-convergence (§3D) and medication sync (§3A): rather than converging demographic/order fields, this pair of events converges **who is on a resident's care team** (`Resident.assignedStaff[]`), the array care-coordination.md's CARE-FR-63/BR-7 depend on for chat eligibility, notification fan-out, and "my residents" staff scoping.

- **CLIN-FR-28 — Practitioner data model & sync.** A new `Practitioner` collection stores one row per `{facilityId, cName, practitionerId}` (unique compound index), each carrying `residentId`, `pcc_patientId`, `status: active|inactive` (default active), `source`, and the full PCC practitioner payload as `practitioner_data` — **field-encrypted** the same way `Medication.medication_data` is (field keys visible, values ciphertext). Encryption uses a **new, resource-agnostic per-resident PCC key** (`Resident.pcc_wrappedKeyB64`) distinct from medication's own dedicated key (CLIN-FR-08) — the two keys and code paths coexist; nothing migrates from one to the other. `syncAndStorePractitioners` fetches the full practitioner list from a **new, second PCC OAuth/mTLS module** (`pcc.core.ts` — duplicates, rather than reuses, the pre-existing `pcc.service.ts` token cache/https agent; see CLIN-GAP-24) and `bulkWrite`-upserts by `{facilityId, cName, practitionerId}`, always setting `status: 'active'` (an upsert alone never marks a practitioner inactive — only a `medicalProfessional.remove` event does, CLIN-FR-28b). (`Practitioner.model.ts`; `pcc.practitioners.ts`; `pcc.core.ts`; `pcc.residentKeys.ts`)

- **CLIN-FR-28a — Practitioner-add event auto-assigns care-team staff.** `medicalProfessional.add` (new event type on the existing `POST /webhooks/pcc`, same unauthenticated exposure as CLIN-GAP-15) resolves the resident by `pcc_patientId`+`pcc_orgUuid`; if no local resident exists yet, it backfills via the same onboarding path as `patient.admit` (silently — no welcome message, since this is a data backfill not a genuine new admission). It then runs a **full** practitioner re-sync (not filtered to the specific practitioner in the webhook payload — a deliberate choice: PCC's practitioner-list read API can lag the webhook, so a filtered fetch risks a zero-match race that silently drops the new practitioner) and, for each returned practitioner, matches `firstName+lastName` (exact, case/whitespace-insensitive) against **active** `Staff` in the facility:
  - **Exactly one match** → `$addToSet`s that Staff's cName onto `Resident.assignedStaff`.
  - **Zero matches** → no assignment, no error.
  - **Two or more matches (ambiguous)** → the system does **not** guess which Staff member is correct. It skips that assignment and sends an internal alert instead — see CLIN-FR-28d.
  (`practitionerSync.ts`; `practitionerStaffAssignment.ts`)

- **CLIN-FR-28b — Practitioner-remove event unassigns care-team staff.** `medicalProfessional.remove` marks the matching `Practitioner` row(s) `status: 'inactive'`, then matches **every** active Staff cName sharing that practitioner's name (not just one — the system cannot know which duplicate-named Staff record, if any, was the one originally auto-assigned) and removes all of them from `Resident.assignedStaff` via `$pull` (which only removes whichever is actually present, so this cannot incorrectly remove an unrelated assignment). A decrypt or match failure is logged and does not affect the practitioner status update. (`practitionerSync.ts`; `practitionerStaffAssignment.ts`)

- **CLIN-FR-28c — Practitioner sync folded into admission & re-admission.** The sync-and-assign pipeline (CLIN-FR-28/28a) now also runs as part of: (1) `onboardNewResident()` — shared by `patient.admit` and `patient.readmit`'s "resident not found" path (CLIN-FR-20a Path B) — alongside the pre-existing medication and contact sync; and (2) `patient.readmit`'s "resident exists" path (CLIN-FR-20a Path A) — previously readmit only converged demographics/status, it now also re-syncs practitioners and re-runs care-team assignment on **every** readmit of an already-known resident. `patient.admit`'s handler required no direct code change to gain this — it is inherited through the shared onboarding function. (`shared/residentOnboarding.ts`; `handlers/patient/readmit.ts`)

- **CLIN-FR-28d — Ambiguous-match alert is an internal ops notification, not a resident/staff-facing feature (judgment call — see below).** When a practitioner's name matches 2+ active Staff, the system emails a **hardcoded list of three named individual addresses** (`DUPLICATE_STAFF_ALERT_EMAILS`, `pardypanda.com` — the implementing engineering team, not a facility contact and not sourced from `Config`) with the facility name, resident name/id, practitioner name/id, and the colliding Staff ids. **This module treats the underlying business rule — "never auto-assign on an ambiguous name match" — as the requirement (folded into CLIN-FR-28a); the specific delivery mechanism (which addresses, what channel) is documented here only as a candidate gap, not elevated to its own resident/family/staff-facing FR**, because: (a) recipients are hardcoded individuals, not a facility or even an environment-configured address; (b) there is no in-app indicator anywhere (admin web, staff app, resident app) that an assignment was skipped — a facility can go indefinitely unaware that a physician failed to auto-attach to a resident's care team. See **CLIN-GAP-23**. (`src/constants/pccAlerts.ts`; `practitionerStaffAssignment.ts`)

## 5. Notifications & real-time behavior

**Largely none**, with two exceptions (both credential/ops-adjacent, neither a clinical-event notification):

- No FCM or socket emission exists for medication changes (including PCC DISCONTINUED/STRIKEOUT events), new lab reports, or directive uploads. *(Backend §1 "Notifications: none"; §9 table contains no medication/lab/ACD row.)*
- **Exception 1 — welcome SMS on PCC-driven admission (CLIN-FR-20d).** When `patient.admit` provisions a new resident's Cognito account, the resident (or, once contact sync runs, their family) receives a custom welcome SMS with credentials and a role-specific app-download link — this is a notification-adjacent side effect of the onboarding automation, not a domain event in the `NotificationConfig` catalog (see announcements-notifications.md / platform-foundation.md PLAT-FR-14c). The prior manager-alert FCM+SMS notification (superseded, CLIN-FR-20d) is no longer sent.
- **Exception 2 — duplicate-staff-match alert email (CLIN-FR-28d, since 2026-08-28).** An ambiguous practitioner-name match sends an email to a hardcoded internal ops address list — see CLIN-GAP-23. This is **not** a resident/family/staff notification (no `NotificationConfig` gate, no FCM, no in-app surface) and is the only notification-shaped output of PCC practitioner sync.
- The resident app's notification center is a passive feed with no mark-as-read and no deep links, so even if events were added, tap-through routing would need building. *(SN app §3.10, §7.9.)*

**Product implication:** a resident currently discovers a new lab report or a discontinued medication only by opening the relevant screen. "Notify resident/family on new lab report" and "notify nurse on critical analyte" are obvious, currently-unbuilt enhancements (the critical flags needed for the latter are already stored — CLIN-FR-14).

## 8. Product-split notes

- **This module is effectively Skilled-Nursing-only in live UX.** The SN resident app ships live Medication List, Test Results, and Advance Care Directive screens against the real APIs. The **Senior Living (assisted-living) resident app renders only mock health screens**: hardcoded medication data (Flomax/Lisinopril), three hardcoded "Healthcare" directive PDFs, and ACD upload/scan buttons that are `console.log` stubs; no health API clients exist in that repo. *(SL app §3.11, §6.1.)* **Gap to decide:** wire the SL app to the same APIs, or formally scope clinical records out of the AL product.
- The product split is **per-app-binary, not runtime-flagged** — both resident apps hit the same backend and tenant model; feature merchandising is hardcoded in each app's Health-hub array. *(SN app §6.)*
- Care level (`assisted_living | memory_care | independent_living | skilled_nursing`) is stored **per resident**, not per facility; nothing in the clinical-records APIs branches on it. PCC and lab integrations are facility-configured (integration records / env), which is what de-facto gates these features to SNF facilities. *(Backend §8.)*
- PCC (an SNF/LTC EHR) medication sync and lab-report ingestion are listed among the explicitly SNF-flavored backend modules; the new automated-onboarding path (CLIN-FR-20d) reinforces this — it is the most consequential SNF-specific backend workflow shipped in the 2026-07 window. **Practitioner sync + auto care-team assignment (§3F) reinforces it further** — it is a purely PCC-gated (i.e. SNF-facility-gated) automation with no equivalent in the AL product.
- The admin web app has **no clinical-records surface** for either product line; its SNF clinical features are IDT reports and referrals (separate modules). A staff-facing medication/lab view in admin web is an open product slot. The doctor e-signature queue (CLIN-FR-19a) is, however, now reachable from the staff **mobile** app (Pending Sign tab) even without an admin-web surface — see referrals.md REF-FR-05a.

## 9. Observations & candidate gaps (with evidence refs)

> Candidate gaps from code review — to be triaged into the backlog, not yet committed requirements. Evidence refs point into `_codebase-analysis/backend-clinical-care.md` (B), `client-resident-app-sn.md` (SN), `client-resident-app-sl.md` (SL), and the 2026-07-12 backend architecture-doc delta review.

**Security / PHI (highest priority)**

- **CLIN-GAP-01 — PHI in logs.** Lemedix webhook handlers log full payloads (demographics, results) via `console.log`; the backend has no structured logger anywhere. *(B §10.2, §10.15.)*
- **CLIN-GAP-02 — Unauthenticated lab webhooks.** Both Lemedix endpoints accept unauthenticated POSTs with no signature verification — anyone who discovers the URL can inject lab reports or patient registrations into the tenant. *(B §2a, §10.2.)*
- **CLIN-GAP-03 — Missing role gates on medication/lab staff reads.** `GET /medications/resident`, `GET /medications/resident/pdf`, and `GET /lab-reports/:residentId` have no role middleware: any authenticated facility identity (including a resident) can pull another resident's medication PDF or lab list by cName/id. Contrast with the ACD staff view, which guards correctly. *(B §1, §2b, §10.3, §4d.)*
- **CLIN-GAP-04 — Fragile lab→resident identity matching.** Reports attach to residents by phone/email match; shared family phone numbers could attach a report to the wrong resident. Facility is verified; identity confidence is not (no MRN/DOB cross-check, no manual-review queue for ambiguous matches). *(B §2a, §10.6.)*
- **CLIN-GAP-20 — Consent-form routes are partly unauthenticated (new, pre-production).** In `consentForm.routes.ts`, **`POST /` (create), `GET /` (latest by residentId), and `GET /:id` carry no `authMiddleware`** — only `POST /pdf` and `POST /sign` do. An unauthenticated caller who can reach the API can **create** a consent form (writing `residentName` + the resident's base64 signature) or **read** a resident's consent form by residentId/id. Same defect class as the unauthenticated `/pcc-sync` (CLIN-GAP-19) and PCC/Lemedix webhooks (CLIN-GAP-15). Backend architecture tracks it as **G-29**. *Candidate fix:* add `authMiddleware` (+ facility scoping) to the create/read routes before production. (`consentForm.routes.ts`)
- **CLIN-GAP-21 — New admin Resident Documents routes lack a role gate (pre-production, NEW, v1.6).** `GET /advance-care-directives/admin/resident/:residentId` and `PATCH /advance-care-directives/:id/view` (added for CLIN-FR-26 / secure-call.md SCALL-FR-08) carry `authMiddleware` but **no `requireAnyRole(STAFF, ADMIN)`**, unlike the doctor-signature routes in the same file which do gate on `requireAnyStaffDesignation`. Any authenticated caller — including a resident or family member — can supply an arbitrary `residentId` and read (or mark-viewed) that resident's directive + secure-call feed, a cross-resident PHI read within the caller's own facility. Lower severity than CLIN-GAP-19 (single-tenant, not cross-facility) but the same missing-role-gate pattern as CLIN-GAP-03. *Candidate fix:* add `requireAnyRole(STAFF, ADMIN)` to both routes. (`advanceCareDirective.routes.ts:44-48`)
- **CLIN-GAP-15 — PCC patient webhook is unauthenticated and logs full PHI.** `POST /webhooks/pcc` has no signature verification or auth (`app.ts:214`); the controller and every handler `console.log` the entire PCC payload and pulled patient data — this now includes the automated-onboarding handler (CLIN-FR-20d), which creates resident and Cognito records off this same unauthenticated trigger, **and, as of 2026-08-28, the two practitioner events (§3F), which can write/remove `Resident.assignedStaff[]` entries off the same trigger**. Anyone discovering the URL can drive resident status changes, trigger resident/Cognito creation, or manipulate care-team assignment; full demographics land in plaintext logs. Same defect class as CLIN-GAP-01/02 (Lemedix). *(`pcc.webhook.controller.ts:19`, `shared/patientData.ts:46`, `updateResidentInfo.ts:16-17,30`.)*
- **CLIN-GAP-19 — New: unauthenticated manual PCC-sync tool writes PHI for an arbitrary `facilityId` (Critical, added 2026-07-10).** `POST /pcc-sync/residents` and `/pcc-sync/residents/map` (`pccSync.controller.ts`, 508 lines) are mounted **outside the `/api` prefix** (`app.ts:242`), so neither the global `facilityMiddleware` nor any `authMiddleware` applies. `facilityId` is read directly from the unauthenticated request body (`pccSync.controller.ts:189-192`); the route file's own comment describes it as an ops tool intended to be "trigger[ed] via Postman/curl," but nothing in the code restricts it to internal-network callers. **This is a cross-tenant PHI-write vector**, not merely a role-gate gap: any caller who can reach the API can write PCC resident-linkage and KMS-encrypted medication data for **any facility**, not just their own. A secondary discrepancy: the route file's own comment says `facilityId` "defaults to `STATIC_INTEGRATION` if omitted," but the controller actually returns 400 when it is absent, and no `STATIC_INTEGRATION` symbol exists anywhere in the config model. Classified **Critical** — same tier as the platform's pre-existing tenant-isolation Blockers (platform-foundation.md §9 items 1–2). A human should confirm whether this is an accepted internal-only tool before it is used to gate a release. *(`docs/reviews/2026-07-12/review-senior_living_backend.md` §"New unauthenticated PCC manual-sync tool," Design Gap G-26.)*
- **CLIN-GAP-22 — New: hardcoded, already-compromised shared secret gates three `/pcc-sync/*` bulk endpoints (Critical, added 2026-08-10/17).** `bulkMedicationSync` (pre-existing, CLIN-FR-22a), `bulkUpdateResidentSync`, and `bulkResidentCognitoSync` (both new, CLIN-FR-27) all check the identical literal `A879B3C-4D5E-6F7G-8H9I-0J1K2L3M4N5O` against `x-sync-secret`/`secretKey` — a string committed in plaintext to source control, so it must be treated as already known to anyone with repo access (current or historical), not merely "an auth gate exists." Unlike CLIN-GAP-19's fully-open sibling routes, these three at least require *something*, but a hardcoded, unrotatable, git-history-visible secret provides negligible real protection for endpoints that create Cognito accounts and write demographic/medication PHI for an arbitrary `facilityId` (same missing facility-header backstop as CLIN-GAP-19 — this router mounts outside `/api`, so no `facilityMiddleware` applies either). Classified **Critical** — same tier as CLIN-GAP-19 and the platform's tenant-isolation Blockers. *Candidate fix:* replace the literal with an env/Secrets-Manager-sourced value at minimum (stopgap), and move toward the same auth model the rest of the API uses (internal-network restriction or a real service credential) before this pattern is extended further. **Do not copy this pattern for any new endpoint.** (`pccSync.controller.ts:346-347,543-544,691-692`; architecture doc G-30.)

**Half-built / write-only data**

- **CLIN-GAP-05 — Lab list pagination broken.** The resident lab list computes `skip` but the query's pagination is commented out — the page param is accepted and ignored; leftover commented code and a query `console.log` remain. *(B §2b, §10.8.)*
- **CLIN-GAP-06 — Single-tenant lab registration mapping.** Patient-registration facility resolution is pinned to `LEMEDIX_FACILITY_ID` ("must be set for the Redwood Grove account") — a second lab-integrated facility cannot onboard without code/config rework. *(B §2a, §10.14.)*
- **CLIN-GAP-07 — LabPatient is a dead-end registry.** Records are stored on registration but never linked to residents and never read by any API. Either link them (improving CLIN-GAP-04 matching) or stop storing them. *(B §2a, §10.9.)*
- **CLIN-GAP-08 — Structured analytes unsurfaced.** `reportFormatAndValues` (values, critical flags, reference ranges, units) is stored on every report but unexposed — the obvious future "lab trends / critical-value alerts" feature has its data layer already built. *(B §2b, §10.9; ties to §5 notification gaps.)*
- **CLIN-GAP-09 — Directive e-signature partly built (staging), now also mobile.** A doctor e-signature flow exists for **staff-authored** directives (`POST /staff` → doctor `pending-signatures` → `PUT /:id/sign`, CLIN-FR-19a), now reachable from both admin web and the staff app's Pending Sign tab. Still absent: witnessing, document-type classification (POLST vs living will vs DNR), and any signature/attestation on the **resident-uploaded** path (CLIN-FR-17 remains upload-only). *(B §4d; SN §3.2; `advanceCareDirective.controller.ts:99-157,495-565`; staff-app review 2026-07-12.)*

**Quality / hygiene**

- **CLIN-GAP-10 — No clinical-event notifications.** No push/socket on new lab report, medication discontinuation, or directive upload (see §5). The one new exception is the welcome-SMS side effect of automated onboarding (CLIN-FR-20d), which is credential delivery, not a clinical-event notification. *(B §1, §9.)*
- **CLIN-GAP-11 — Hardcoded fallbacks.** Process-wide (not per-facility) timezone defaulting to `America/Los_Angeles`; medication-PDF facility name falls back to a raw facilityId or the literal `'Shashi.ai'`; PCC patient-search `facId` defaults to `'12'`. *(B §10.14, §10.18.)*
- **CLIN-GAP-12 — Schema typo as API surface.** `IntegrationAvailable.timzone` (sic) drives medication date formatting; renaming later is a data migration. *(B §10.13.)*
- **CLIN-GAP-13 — SL resident app mock screens present clinical features that don't exist.** Demo builds over-credit the AL product (mock meds, mock directives, stub upload buttons) — a PRD/demo-integrity risk until the screens are wired or removed. *(SL §3.11, §6.1.)*
- **CLIN-GAP-14 — No resident-app notification of medication "source of truth".** The resident list silently merges manual self-entries with PCC-synced orders with no provenance indicator in the UI; a resident-entered record and an EHR order render alike. *(B §1; SN §3.2 — inferred from display model; verify before committing as a requirement.)*
- **CLIN-GAP-16 — `Transferred` status is dead-write.** The resident `status` enum retains `Transferred` (PLAT-FR-52) but `buildPatientStatus` collapses every non-discharged state to `Active`, so transfer/cancelTransfer events now record `Active`, not `Transferred`. Any UI/report branching on `Transferred` is dead for PCC-synced residents. *(`shared/patientData.ts:72-74`; `transfer.ts:13`.)*
- **CLIN-GAP-17 — PCC status correctness depends on the re-pull, not the event.** Because all handlers ignore the event semantics and re-derive from the pulled `patientStatus`, a stale or eventually-consistent PCC read at webhook time can momentarily set the wrong status (e.g. a `readmit` that pulls before PCC flips `patientStatus` keeps the resident `Discharged`). No retry/reconcile exists; `fetchPccPatientData` returns `null` and silently skips on missing resident/config (same silent-drop pattern as BR-07). *(`shared/patientData.ts:16-46`.)*
- **CLIN-GAP-18 — `readmit` does not clear `deletedAt`.** `patient.readmit` (CLIN-FR-20a) sets `status: Active` via `buildPatientStatus` but never clears the soft-delete flag, so a readmit on a previously deleted resident produces a contradictory `deletedAt`-set + `status: Active` record that remains hidden from `deletedAt: null` listings. **Now a scoped build item** — the convergent-state model must clear `deletedAt` whenever derived status ≠ `Discharged`, matching the manual re-admission rule (PLAT-FR-59). Tracked: `SL-TD-07`; depends DC-08 to test. *(`handlers/patient/readmit.ts`; `shared/patientData.ts:71-79`.)*
- **CLIN-GAP-23 — Duplicate-staff-name alert has no facility-visible surface and hardcoded personal-email recipients (new, 2026-08-28).** `DUPLICATE_STAFF_ALERT_EMAILS` (`src/constants/pccAlerts.ts`) is three named individuals' `pardypanda.com` addresses — not sourced from `Config`, not per-facility, not rotatable without a code deploy. Judged **not** to warrant its own resident/family/staff-facing PRD requirement (CLIN-FR-28d treats the underlying skip-on-ambiguity *business rule* as the requirement; this gap is about the *notification mechanism* only). When triggered, a resident can be left with **no physician auto-attached to their care team**, and nothing in admin web, the staff app, or either resident app indicates this happened. *Candidate fix:* source recipients from a per-facility (or at minimum env-configured) ops contact, and/or surface skipped assignments as an admin-visible worklist item. (`pccAlerts.ts`; `practitionerStaffAssignment.ts`)
- **CLIN-GAP-24 — Practitioner sync introduced a second, independent PCC OAuth/mTLS module (new, 2026-08-28).** `pcc.core.ts` re-implements `resolvePccConfig`/`getPccAccessToken`/`getPccHttpsAgent` from scratch rather than importing the identical, pre-existing functions in `pcc.service.ts` — two separate in-memory OAuth token caches and two separate mTLS agents for the same PCC client now coexist per process. Not currently harmful, but a future auth-flow fix applied to one module will silently not apply to the other. *Candidate fix:* consolidate on one module. (`pcc.core.ts`; `pcc.service.ts`.)

**Explicitly absent (net-new if required):** eMAR/administration tracking, refill requests, adherence logging, vitals, medication interaction checking, lab-result trend charts, ACD e-signature on the resident-upload path, family-specific clinical consent controls, any read/write API or admin surface for `Practitioner` records themselves (§3F). *(SN §3 "Explicitly absent"; B §§1–2, 4d.)*
