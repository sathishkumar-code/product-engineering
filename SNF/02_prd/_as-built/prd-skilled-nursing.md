## 1. Product overview

**Skilled Nursing** extends the shared senior-care platform into the skilled-nursing-facility (SNF) setting: shorter, clinically intensive stays oriented around rehabilitation, interdisciplinary care planning, and discharge. It layers a clinical and care-coordination product on top of the same hospitality/operations base that Senior Living uses (dining, wellness services, transport, housekeeping, activities, announcements, TV).

**Client distinctness (load-bearing).** The Skilled Nursing resident experience ships as its own dedicated mobile app, `senior_living_skillednursing_resident` — a **separate binary from the Senior Living resident app** (`senior_living_reactnative`), not a facility-type conditional inside a shared app. Both apps hit the same `senior_living_backend` (port 7000, `x-facility-id` multi-tenancy, Cognito auth) and share structural DNA (Redux Toolkit, the `CustomBackground` pub/sub theming system, AsyncStorage token storage, Socket.io chat), but the Skilled Nursing app is materially more clinical: it is the only resident client with Advanced Care Directives, Rehab (PT/OT/ST scheduling + history + report + message-the-rehab-team), Lab Reports / Test Results, and Care Conferences. **As of `origin/master` HEAD `4734daf` (2026-08-21) it authenticates passwordless** — a phone-or-email identifier plus a Cognito `EMAIL_OTP`/`SMS_OTP` challenge, driven directly against Cognito from the client (vs. the Senior Living app's email + password + TOTP) — superseding the phone+password+SMS-MFA model this doc previously described and the custom-OTP password-reset flow that went with it (both retired from this app; see platform-foundation.md PLAT-FR-72a). It still carries a HIPAA inactivity auto-logoff gate not present on the Senior Living app (though its `IDLE_TIMEOUT` remains a 7-day no-op, see prd-skilled-nursing.md §6). Product/engineering decisions that treat "the resident app" as singular must specify which of the two binaries they mean.

What the product adds for each user group:

- **Patients/residents** get a dedicated mobile app with their medications, lab results, rehab schedule and history, secure chat with their care team, advance care directives, brain games, activities RSVP, a unified agenda, and TV pairing — alongside the shared dining/transport/housekeeping/salon self-service.
- **Family members** are managed by the resident (up to 4), participate in care conferences, and can act for the resident where policy permits.
- **Clinical staff** (Nurse, Case Manager, Social Worker, Doctor, Dietitian, rehab team) are first-class: assigned to each resident (now via the resident's single `assignedStaff[]` care-team set), gating chat access, attributed in IDT reports, staffing rehab appointments, and signing referrals (doctor e-sign on advance care directives and referrals — now reachable from a dedicated staff-app mobile surface as well as the admin web, see §7 item 1). Case Manager / Doctor / Director of Nursing / Social Worker additionally have a dedicated staff-app mobile experience on `staging`.
- **Facility admins** run the SNF roster (case manager / social worker / doctor columns), the rehab suite (therapy catalog, appointments, calendar, team, availability, messages), IDT reports, care conferences (Zoom or in-person with recordings/transcripts), referrals to home-health agencies with in-house e-signature, and everything in the shared operations base.

## 3. Personas

See [personas-and-roles.md](./personas-and-roles.md). SNF-specific notes:

- **Care team** (Nurse, Case Manager, Social Worker, Doctor, Dietitian) is a behavior-bearing designation group: chat gating, resident assignment (the resident's `assignedStaff[]` set), IDT attribution.
- **Rehab group** (Director of Rehab, Rehab Therapists / Rehabilitation Specialist) staffs the rehab engine and manages weekly availability.
- 13 SNF leadership designations form a supervision group; none have dedicated mobile experiences yet.
- Patients authenticate in the SN app **passwordlessly** (phone-or-email + Cognito `EMAIL_OTP`/`SMS_OTP`, as of 2026-08-21 — platform-foundation.md PLAT-FR-72a), replacing the SN app's prior phone+password+SMS-MFA model; the SL app still uses email + password + TOTP. This is no longer just a field-convention inconsistency — the two resident apps now run structurally different auth mechanisms.

## 5. Product-level requirements (cross-cutting)

Shared requirements SL-PR-01 … SL-PR-07 from the [Senior Living PRD §5](./prd-senior-living.md) apply identically (facility scoping, Cognito auth, slot pipeline, UnifiedSchedule, notification platform, permission-gated admin, payment history). Additional SNF-specific requirements:

- **SN-PR-01 — Care-team integrity.** Every SNF resident carries an assigned care team, modeled as a single flat `assignedStaff: string[]` set of staff `cName`s (this replaced the five legacy per-role fields — nurse/caseManager/socialWorker/doctor/dietitian — on `staging`, with a one-time `migrateAssignedStaff.ts` backfill). These assignments gate chat initiation, populate IDT/referral/IDT-report context, drive assigned-care-team notification fan-out, and surface on the roster.
- **SN-PR-02 — Clinical data protection.** Clinically sensitive payloads are envelope-encrypted at rest with distinct KMS schemes per domain (PCC medications per-resident; rehab messages per-field; chat per-conversation). PHI-bearing documents (med lists, lab reports, referrals) render as PDFs via signed URLs.
- **SN-PR-03 — External clinical interoperability.** The product ingests from PointClickCare (a full **patient-lifecycle webhook set** — admit/update/discharge/readmit/cancelAdmit/cancelDischarge/transfer/cancelTransfer plus **updateContactInfo** (resident + family-member contact sync), 14 handlers total) and lab providers (Lemedix/CrelioHealth webhooks → resident-visible reports). **As of 2026-07-10, PCC admission (`patient.admit`) is fully automated end-to-end**: the handler resolves the facility by `orgUuid`, **creates the `Resident` document**, **provisions a Cognito account by phone** (with the invite SMS suppressed in favor of the platform's custom welcome-SMS/app-link message — platform-foundation.md PLAT-FR-14c), and **fetches, encrypts, and upserts the resident's PCC medications** — a rewrite of the prior "notify active managers to add the resident manually" behavior (still available as a fallback for non-PCC facilities). **As of staging the same onboarding automation is extended to `patient.readmit`** when no local resident exists (returning discharged patients), with the onboarding logic extracted into a shared `residentOnboarding` service; `patient.updateResidentInfo` likewise auto-provisions when a phone is added to an existing resident. Contact sync (family members) now runs on admit/readmit/updateResidentInfo, preserves each contact's own `cName`, and populates `familyMember.phoneList[]`. The convergence subset of the remaining patient handlers drives resident `status`/`dischargeDate`/`unitNo` via authoritative re-pulls (CLIN-FR-20/21). Referrals to home-health agencies are exported by **fax via WestFax** (**pre-production**): a Send-to-Agencies action records a `ReferralSentHistory` snapshot (`POST /api/referrals/:id/sent-history`) — with dedup that skips documents an agency already received — and a background `POST /api/fax/westfax/send` faxes each document to each agency's `faxNumber`, tracked per-fax in `FaxLog` with a delivery webhook, a retry path (`POST /api/fax/westfax/retry`), and a facility-name CSID. This supersedes the prior AWS SES email path (`send-referrals-emails`); the generic Documo fax route (`POST /api/fax/send`) is separate and not the referral channel. PCC reads gained 401-token-cache and 5xx retry/skip resilience so a transient PCC outage degrades to "no update this event" (CLIN-FR-07). Integration availability is per-facility (`IntegrationAvailable`, `Config.pms`; WestFax creds under `IntegrationAvailable(name:'westfax')`). See [referrals.md REF-FR-09/09a](./modules/referrals.md) and [clinical-records.md CLIN-FR-20d](./modules/clinical-records.md) for full detail.
- **SN-PR-04 — Signed clinical documents.** Referral approval embeds the physician's signature image into a regenerated PDF and records an immutable audit trail (signer, timestamp, IP, user agent). Signed documents are immutable thereafter. As of staging, both the referral e-sign and the ACD staff-authored e-sign queues are also reachable from a dedicated staff-app **Pending Sign** mobile surface for doctor-designation users (see referrals.md REF-FR-05a).
- **SN-PR-05 — Conference lifecycle automation.** Care conferences progress SCHEDULED → IN_PROGRESS (cron-driven at T-5min) → IN_REVIEW (recording attached) → COMPLETED/CANCELLED; virtual conferences provision Zoom meetings, in-person ones attach S3 audio with Lambda-generated transcripts; summaries may be shared to the resident.
- **SN-PR-06 — Interdisciplinary reporting.** IDT reports attribute sections by submitter designation (case manager / rehab / social worker) and auto-promote to SUBMITTED when all three roles have contributed.

## 7. Top observations & candidate gaps (rollup)

Module §9 sections carry the evidence-cited detail. SNF headlines:

1. **Clinical-role mobile gap — further closed (staging → 2026-08-21).** Case Manager / Doctor / Director of Nursing / Social Worker have a dedicated Skilled Nursing staff-app experience (care conferences, IDT/rehab reports, medications, chat), chat reaches every staff member, and the doctor's referral/ACD e-signature queue is reachable from a mobile **Pending Sign** tab. **New 2026-08-21:** Case Manager/Social Worker/Director of Nursing additionally gained a real-time **Transport** tab and a **Documents/Scan** tab (transportation.md TRN-FR-25) — whether the Transport tab duplicates or deliberately splits from the pre-existing case-manager Transport screens is an open product question (transportation.md §9 O17). A device-level **biometric App Lock** now gates every PHI screen on this app (platform-foundation.md PLAT-FR-75) — enrollment is device-level, not account-level, worth a product/security decision for shared facility devices. Remaining gaps: Nurse, rehab therapists, and dietitian have no task experience (dietitian is chat-only; a `DietitianView` is built but unwired); the Reports tab is dead code (commented out, unrelated to the Pending Sign or Transport additions — needs a product decision on whether it was intentionally retired); and the app-flow gating is client-side off a hardcoded `ROLE_GROUP_FLOW_MAP`. *(personas §2.2; messaging-chat §9; transportation.md §9 O17; platform-foundation.md §9 item 39; care-coordination §9)*
2. **PHI / auth-surface candidates — new Critical item added 2026-07-10.** Lab webhooks are unauthenticated and log PHI; medication/lab staff reads lack role gates; `GET/DELETE /care/:id` is unauthenticated; a **new unauthenticated `GET /api/residents/pcc-contacts`** fetches PCC family-member contacts on demand; the new `/api/fax/*` routes' facility+auth guards are **bypassable via `FAX_LOCAL_BYPASS=true`** with no production fail-closed. **New this window:** `POST /pcc-sync/residents` and `/pcc-sync/residents/map` (senior_living_backend, merged 2026-07-10) are **unauthenticated, unscoped-by-facility-header** endpoints that write PHI (resident PCC linkage + KMS-encrypted medications) for **any `facilityId` supplied in the request body** — a manual "trigger via Postman/curl" ops tool with no auth posture at all. Classified Critical, same tier as the pre-existing tenant-isolation Blockers; a human should confirm whether this is an accepted internal-network-only tool before it blocks a release. (The previously-flagged double-mount of `/api/reports` is now **resolved** — single mount.) Contract-level findings for the technical evaluation. *(clinical-records §9 CLIN-GAP-19; care-coordination §9)*
3. **Single-tenant integration shortcuts** — `LEMEDIX_FACILITY_ID` env mapping and hardcoded timezone undermine the multi-tenant model for clinical ingestion. The staff app has since added a client-side facility-configured IANA timezone layer (platform-foundation.md PLAT-FR-15a), but this does not change backend ingestion/cron timezone behavior. *(clinical-records §9)*
4. **Orphaned SN-app clinical screens** — a rebuilt PT/cognitive/outside-agency booking flow exists against `/care` but is unreachable; decide build/remove. *(therapy-rehab §9)*
5. **Dual therapy engines** — the AL `/care` path and SN `rehab/*` path implement overlapping scheduling logic twice; the fork is the canonical example of the platform's emergent product split. *(therapy-rehab §8)*
6. **Referral status centralized + renamed; WestFax now pre-production.** The status set was moved into a single `REFERRAL_STATUS` constant and **renamed** to `Incomplete → Pending Signature → Ready to send → Sent` (**pre-production**; a one-time `migrate-referral-status.ts` rewrites stored values and **must still run against `production` before that promotion** — §9 O-10). Referrals carry a required `assignedPhysician` (Staff ref) plus `createdBy`/`updatedBy`, embedded `additionalDocuments[]`, `additionalNotes`, and `includeMedicationList`; `pcpFollowUp` was dropped and `selectedHHA` is now vestigial. `Sent` is auto-applied when a send is recorded; signer authorization was tightened to the `assignedPhysician` (O-3, partial). **Remaining pre-production→production blocker:** the WestFax delivery webhook is still unauthenticated (§9 O-8 / backend architecture G-28) even though the hardcoded-staging callback URL was fixed (O-9 resolved). *(referrals §3 REF-FR-03/09, §9 O-3/O-8/O-9/O-10)*
