## PRD Review (Round 1)

**1. PRD §4 and A7 instruct against reusing the existing `Staff.availability` field/endpoint — Sathish's technical decision on this design goes the other way.** §4 states plainly: "This feature should not reuse that endpoint or its underlying model; it needs its own." Per Sathish's direct decision during this review (2026-08-21), the TD instead extends and repairs the existing `Staff.availability` field (renaming its current content into `therapistBookingSlots` and adding `workHours`/`manualOOO` alongside it, plus fixing the `staff/availabilty` typo as part of the same migration — TD §3.2, §5, §9). This is a real divergence between the PRD as written and the technical direction actually being built, not a nuance — recommend updating PRD §4's data-source note to reflect the decision, so a future reader doesn't take the PRD's "needs its own" framing at face value against a TD that does the opposite. Not a blocking defect; flagging so the two documents don't quietly disagree.

**2. BR6a's OOO-start notification, read literally, likely over-fires.** BR6a says the notification fires "when someone's OOO begins (automatic or manual)... at the time their regular work starts." Automatic OOO begins every single evening and every weekend for literally every staff member under A2/A11's own definition — if BR6a is implemented as written, a facility-wide "advance notice" notification would fire for nearly every staff member every single work-day morning, which is hard to square with the PRD's own stated business goal ("without adding another push-notification channel to an already over-notifying platform," header table). The TD (§3.5, §11 TD-1) proceeds on the assumption that this is meant to be scoped to manual OOO periods beginning today, not literal automatic transitions, and flags it as the standout open question rather than silently building the literal reading. This should be confirmed with Product before Epic/Story creation for this specific behavior — it changes both the cron design and the actual day-to-day notification volume staff will see.

**3. §4's facility-timezone assumption (A12) lands on an unresolved platform question (ADR-005), same gap the Director Ops Dashboard PRD hit.** ADR-005 is `Proposed`, not decided — only the staff app currently treats facility time as authoritative for computation. Per the same approach Sathish already approved for the Director Ops Dashboard, the TD resolves this server-side, scoped to this feature's own endpoints and cron (TD §3.4), rather than replicating the staff app's client-side timezone library across four more surfaces or waiting on the platform-wide decision. No PRD change needed — flagging for visibility, and because this is now the *second* feature independently cutting the same corner around ADR-system-wide the same way; worth the ADR-005 owner's attention that a pattern is forming.

**4. PRD's own IQ-04 (facility-contact field for the resident-app affordance, referenced in §4) is resolvable now.** `Config.facilityPhone` exists as an existing String field (`data-schema.md` §2.31, "Facility identity fields") — recommend PRD §4 be updated from "not confirmed which exact field" to name this field directly, since it was confirmed during this review.

**5. Minor, non-blocking: PRD A9 assumes a specific, already-shipped "select physician to send for signature" screen, but this review could not independently confirm which as-built component that is.** The closest candidate found is the referral-creation form's `assignedPhysician` selection (`referrals.md` REF-FR-07) — reasonable, but not a named, confirmed match. Recommend whoever validated A9 with product confirm the exact component before Story-writing for that specific badge-integration point (TD §11 TD-3).

### Findings

Comparison run 2026-08-21 against `ooo-technical-design_v1.md`, which appeared in the same folder after this TD was authored. v1 is organized clearly and covers the same functional ground (data model, API, caching, notifications, frontend, permissions, testing, rollout), but several of its concrete technical choices don't match this codebase and would need correction before anyone could build against it directly:

1. **Wrong database engine.** v1's entire §3/§9 is Postgres DDL (`CREATE TABLE`, `gen_random_uuid()`, `CHECK` constraints, SQL foreign keys). Every reviewed as-built source (`data-schema.md`, `Staff.model.ts`, `Config.model.ts`) confirms this platform is MongoDB/Mongoose throughout, with `facilityId` as an unenforced string tenant key (`technical-debt.md` T8), not a relational FK. None of v1's schema is directly usable as written.
2. **Misses the existing `Staff.availability` field entirely.** v1 proposes a brand-new `staff_availability` table with no reference to the field the PRD itself calls out by name in §4 ("a buggy, typo'd rehab-therapist appointment-slot availability endpoint... should not reuse that endpoint or its underlying model") or to `technical-debt.md` item 18 (`PUT staff/availabilty/:staffCName`). This TD's central data-model decision (extend/rename that field, per Sathish's call) has no counterpart in v1 at all — v1 never surfaces the collision risk because it never found the existing field.
3. **Invents infrastructure not present in the codebase.** v1's OOO-start notification (§8.2) is built on a generic job queue ("Bull, RabbitMQ, or Temporal"). The platform's actual pattern for timed/deduplicated sends is a per-minute cron plus an atomic-insert dedupe claim (`NotificationSentLog`, `announcements-notifications.md` ANN-FR-18) — no job-queue dependency exists anywhere in the reviewed architecture. Building against v1 as written would mean introducing a new piece of infrastructure the rest of the platform doesn't use for this exact same problem.
4. **Treats ADR-005 as already decided.** v1's §9.2 states its timezone approach "follows ADR-005" as settled fact. ADR-005 is `Proposed`, not decided — only the staff app has implemented anything like facility-time authority, and admin web/resident apps/backend cron are explicitly unaudited. This TD (§3.4) treats that as an open platform question and scopes a feature-local resolution instead, consistent with the same call already made for the Director Ops Dashboard TD.
5. **Implements BR6a's notification literally, without flagging the volume problem.** v1 §4.6/§8.2 schedules the OOO-start push "when a Manual OOO record is created **or an automatic OOO triggers**" — built exactly as BR6a reads, with no note that this would fire a facility-wide push for nearly every staff member every work-day morning (automatic/after-hours OOO happens nightly for everyone). This is Finding 2/TD-1 above; v1 doesn't surface it as a risk at all.
6. **No citations to as-built sources.** v1 doesn't reference a single existing FR/BR/ADR ID, model file, or architecture doc beyond the PRD's own numbering — every design choice reads as a plausible generic implementation rather than one checked against what already exists in this codebase.

**What v1 does better, worth folding into the standard TD as an addendum rather than dismissing wholesale:** a concrete monitoring/alerting section with specific thresholds (§13.2 — cache hit rate <80%, notification latency >5s, job-queue-depth-style backlog growth), an explicit phased rollout (internal → pilot facilities → GA) more granular than this TD's §9, and runnable-shaped TypeScript sketches for the permission guards and service methods that give engineers a faster starting point than prose alone. Recommend appending a lightweight "Observability" subsection to `feature-out-of-office_TD.md` §9 borrowing v1's concrete alert thresholds (adapted to the cron-based architecture actually being built), rather than adopting v1's schema or infrastructure choices.

**Recommendation:** `feature-out-of-office_TD.md` remains the design of record — it's the one directly buildable against this codebase's actual stack (Mongoose, cron+dedupe, the existing `Staff.availability` field). v1 is useful as a generic best-practice checklist and for its monitoring-section detail, but not as an implementation blueprint; it should not be promoted or merged as-is.
