### 2. The Calendar's own status filter already excludes `COMPLETED` (BR-12) — the ER's "every other status opens read-only" rule may be unreachable for `COMPLETED` on the Calendar specifically, and the ER doesn't address the interaction.

`care-coordination.md` BR-12 and CARE-FR-26a both document that `CareConferenceCalendar.tsx`'s own data fetch (`GET /care-conference?...status=SCHEDULED,IN_PROGRESS,IN_REVIEW,CANCELLED&...`) already omits `COMPLETED` — a client-side query choice, not a backend restriction — so a completed conference never appears on the Calendar to be clicked on in the first place, even though it's visible in the List screen's History tab.

The ER's item 1 (§2) frames the status-gated popup rule as applying identically "on row-click (List) or event-click (Calendar)," including for `COMPLETED`. As written, that part of the rule is currently unreachable on the Calendar — a developer could build the popup-mode logic exactly as specified and never notice `COMPLETED` conferences simply never reach it via that surface, because BR-12's filter drops them before they render.

**Recommendation:** this needs an explicit scope call from Product/Sathish, not an SA-side assumption either way: either (a) note that `COMPLETED` read-only viewing under this ER's rule is List-screen-only until BR-12 is separately fixed, or (b) fold extending the Calendar's status filter to include `COMPLETED` into this ER's scope so the rule is actually reachable on both surfaces for all four non-`SCHEDULED` statuses. Neither is currently stated in §3.1/§3.2.

### 3. `ModuleKey` is a closed type today with only one literal value — adding `care-conference` is a small backend code change, not purely config + template as the ER's Notes to SA imply.

`architecture-senior_living_backend.md`'s v2.6 delta (code-verified against `pre-production` HEAD `27361392`) documents `Config.chat.moduleMessageBindings?: Partial<Record<ModuleKey, ...>>` with **`ModuleKey` currently only `'TRANSPORTATION'`**. The ER's Notes to System Architect ask me to *"confirm `moduleMessageBindings`/`ChatSystemUser` can support a second `ModuleKey` (`care-conference`) without changes beyond config + a new template/`resolveMentions`"* — it cannot, quite: the `ModuleKey` TypeScript union itself has to gain the new literal before any `sendModuleMessage()` call can type-check against it. This is low-risk, low-effort, but it is a real source change in `senior_living_backend`, not a config-only or template-only addition, and should be tracked as such (Technical Task, below) rather than discovered mid-build.

Separately: the existing literal is uppercase (`'TRANSPORTATION'`), while both `messaging-chat.md`'s PRD-level as-built and this ER write the example/proposed key in lowercase-hyphenated form (`'transportation'` / `'care-conference'`). Recommend the new value follow whatever the actual code casing convention turns out to be (plausibly `'CARE_CONFERENCE'`) rather than the ER's `'care-conference'` — confirm during the same spike as Finding 1/3's other code check.

### 4. `PUT /care-conference/{id}`'s current status gating is genuinely undocumented — the ER correctly flags this as an open item, and I can't resolve it from any as-built layer.

I checked all three as-built layers (PRD-level `care-coordination.md`, codebase-analysis `client-admin-web.md`, and the code-level `architecture-senior_living_backend.md`) specifically for the general update endpoint's status restriction. Only `PUT /:id/update-summary`'s gating (`IN_REVIEW`/`COMPLETED`-only) is documented at that level of detail; the plain `PUT /:id` handler's status behavior isn't covered anywhere I could find. The ER's own "Notes to System Architect" already asks for this to be confirmed — I'm affirming it's a real gap in the documentation (not something I missed by not looking), and it needs a direct read of `careConference.service.ts`'s update handler (adjacent to the already-cited `:775`/`:796-839` line references for the sibling methods) before the backend piece of this ER can be sized at all: it's either a zero-line no-op (already `SCHEDULED`-only) or a net-new validation branch, and those are very different amounts of work.

### 5. HIPAA / PHI walk-through (per the hipaa-compliance-check skill)

- **Access control / minimum necessary (content):** satisfied at the message-content layer — the ER commits to resident name, date, and time only, no notes/agenda/attendees. Good.
- **Access control / minimum necessary (audience):** not addressed. The chat group receiving this notification is manually configured per facility and isn't scoped to the roles CARE-FR-26 already restricts conference *visibility* to (host-scoped for non-admin staff, full visibility for admins). This ER's own Impact section already flags that this is new PHI exposure "to everyone in that facility's configured chat group," which is the right instinct — but nothing in the ER (or in CARE-FR-26/26a) constrains who ends up in that group at provisioning time, and building that constraint isn't in scope here (manual provisioning is explicitly out of scope per §3.2/EQ-05). Recommend this land as an explicit operational note for whoever provisions the "Care Conferences" chat group, and as a consideration for the future self-service admin UI the ER already earmarks separately.
- **Audit logging:** no new gap — automated messages ride the same `sendMessage()` persistence/audit path as any human message (MSG-FR-36), same as Transportation's existing precedent.
- **Encryption:** no new gap — inherited from `sendMessage()`'s existing encryption pipeline.
- **Retention/disposal:** worth stating explicitly rather than leaving implicit — the backend's chat retention policy is "fully non-destructive" (soft-deleted messages/destroyed conversations are never physically purged, per the 2026-08-20 architecture delta's stated HIPAA/CA 7-year rationale). This means the resident-name/date/time PHI this ER introduces into chat is retained indefinitely under that existing policy. Not a new gap this ER creates, but the compliance register entry (below) should say so plainly instead of silently deferring to "platform default."
- **Third-party/integration exposure:** none — entirely internal to `ChatSystemUser`/`moduleMessageBindings`, no PCC/Epic involvement.
- **Breach-readiness:** genuinely new PHI exposure surface, as the ER's own Impact section already says. I checked and **there is no existing `hipaa-compliance-register.md` entry for the `ChatSystemUser`/`moduleMessageBindings` mechanism at all** — not even for Transportation's own precedent-setting use (TRN-FR-26), which has been live since the 2026-08-20 window. This is a good moment to log one entry covering the general pattern plus this ER's specific new exposure, rather than a care-conference-only note. Per the register's access restriction, I'm proposing the entry text here for Sathish to add, not writing it myself:

  > **Current State:** No facility-wide chat notification exists for care-conference lifecycle events today; conference visibility is limited to host-scoped/admin-scoped reads per CARE-FR-26. Transportation (TRN-FR-26) already uses the same `ChatSystemUser`/`moduleMessageBindings` mechanism to post ride-lifecycle cards into a facility chat group, live since 2026-08-20, with no register entry logged for it to date.
  > **Gap-Risk:** This ER adds `care-conference` as a second consumer, posting resident name + date + time into a facility-configured chat group on schedule/edit/cancel. Message *content* is minimized (name/date/time only), but message *audience* is not scoped to CARE-FR-26's existing view-access roles — anyone manually added to the configured chat group receives this PHI regardless of whether they'd otherwise have visibility into that conference. Same underlying gap already exists, unlogged, for Transportation.
  > **Recommended Fix:** No code change required for this ER (content minimization already covers the immediate risk). Document/operationally restrict chat-group membership to roles with existing CARE-FR-26-equivalent visibility at provisioning time; revisit as an enforced constraint if/when the self-service `moduleMessageBindings` admin UI (flagged as a future enhancement by this ER, EQ-05) is built.
  > **CFR reference:** 45 CFR §164.502(b) / §164.514(d) (minimum necessary standard).
  > **Notes:** Retention follows the platform's existing non-destructive chat retention policy (indefinite retention of soft-deleted content) — not a new behavior, but now applies to this new PHI category too.
