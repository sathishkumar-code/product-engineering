# Sprint Retrospective Template

Standard structure: metrics, then a reflection format, then concrete action items.
The reflection format itself is interchangeable — several industry-standard
variants are listed at the end — but the metrics and action-items sections should
stay regardless of which reflection format the team uses.

```markdown
# Sprint <N> Retrospective — <Product: Core / SAL / SNF>

| Field | Value |
|---|---|
| Sprint dates | |
| Attendees | |
| Facilitator | |

## 1. Sprint metrics
| Metric | Planned | Actual |
|---|---|---|
| Points/items committed | | |
| Points/items completed | | |
| Stories carried over | | |
| Mid-sprint scope changes | | |

Pull these from the tracker at sprint close, not from memory or the sprint-plan
doc's original commitment alone.

## 2. What went well

## 3. What didn't go well

## 4. Action items
| Action | Owner | Target date | Status |
|---|---|---|---|

Make these concrete enough to become tracker tasks themselves if warranted — a
vague action item ("communicate better") rarely survives to the next retro; a
specific one ("add a mid-sprint check-in on Wednesdays") can be checked.
```

## Alternate reflection formats
Section 2/3 above ("What went well / What didn't go well") is the default. Any of
these can substitute for it — keep sections 1 and 4 either way:
- **Start / Stop / Continue** — what to start doing, stop doing, keep doing.
- **4Ls** — Liked, Learned, Lacked, Longed for.
- **Mad / Sad / Glad** — useful when team morale itself needs surfacing, not just
  process issues.

Rotate formats occasionally if retros start feeling rote — a repeated format can
produce repeated, shallow answers.
